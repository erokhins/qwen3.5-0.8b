# `engine/` — weight residency (W5 first half)

**Two device experiments stand between this file's launch configurations and "trusted", and neither
has ever run.** Nothing in `engine/` has touched a device, so these are not polish: **E1** decides a
numerics question that no other criterion on a norm can see, and **E2** decides a 0.279 ms/token
performance claim imported from a different host. Commands are in `README.md`'s device list; no
ledger row should be written from the prose below until they have run.

* **E1 — glue's correctness gate at 1024 threads.** The engine launches `glue_add_norm<256>`, the
  width the 784-comparison gate actually ran at, because `glue_kernels.h:83-102` derives
  `PER = H/THREADS`: 256 → 4 elements/thread then an 8-partial warp tree, 1024 → 1/thread and a
  32-partial tree. That is a **different F32 summation order for the mean of squares**, and a norm's
  legal floor is 1 ULP with no cancellation band, so the only criterion that can tell the two apart
  is `ndiff` — which `prototype/glue/results.md:113` names as "the criterion doing the work". The
  published floor (3 / 393 216) was measured on the 256-thread order, so the 1024 order the sweep
  prefers (≈2.78 vs 3.75 µs/launch, §4 there) has no floor measurement at all; `results.md:170`
  asks for exactly this re-run and `:230` still lists it open.
  *Expected:* `784 comparisons`, 0 failures, ndiff at the same floor. *Failure mode that matters:*
  the gate passes at 1024 only by loosening `NDIFF_PCT_MAX`, or the ndiff count moves enough that
  "same arithmetic, different width" is false — in which case 256 is not a preference but a
  requirement and the sweep's 1024 row needs the caveat. (A CPU pre-answer to the floor half exists:
  `floor_probe.py`'s `THREADS = 256` constant is a numpy mirror of the order, not device code.)
* **E2 — `proj_gemv` PACK_X=false vs true, cold, on the engine's own launcher.** The engine now
  instantiates `PACK_X=false` (`kernels_proj.cpp`), which is both the gated config and the measured
  faster one — but both numbers (2.991 vs 3.269 ms) come from `prototype/proj_gemv`'s host at its own
  geometry, and `PACK_X=false` makes the caller hand F32 `x`, so ≈48 cast launches/token (≈0.089 ms
  at the 1.85 µs floor) come back into the plan. The comparison has never been made on the engine's
  launcher, and cannot be until `decode_step` exists.
  *Expected:* unpacked ≤ packed − casts, i.e. the prototype's ordering reproduces, ≈0.28 ms/token
  between the configs. *Failure mode:* if packed-with-casts wins on the engine's geometry, `false` is
  the wrong constant and `kernels_proj.cpp`'s comment must carry the engine's own number instead of
  the prototype's. Repeatable-now half (prototype token plan, same quiescent window):
  `--time --sweep`, which prints both rows.

Status: **gate PASS — 52 checks, 0 failures** (`engine/loader_test`, built by
`engine/build.sh`). Residency only: no token loop, no per-request state, no kernel calls
(`README.md`). Binary: `engine/loader_test`. Gate: `engine/loader_test` itself; its
per-tensor shape/dtype reference is generated by `engine/weights_reference.py`, which
reuses `tools/weights_report.py`'s own header reader and byte assertion.

```bash
./engine/build.sh && ./engine/loader_test          # from the repo root
./engine/loader_test --no-verify                   # skips sections 8's copy-back+hashing
```

**Every timing here is provisional.** `tools/gpu_lock.sh util` read 95–99 % at both ends of
every run: `flash_serve` — the server producing this session's own tokens — polls the iGPU
and is outside the lock (`gpu_lock.sh` records util and deliberately does not gate on it).
Correctness claims are unaffected; bandwidth numbers move by more than 2× between runs.

## The D2H discrepancy: measured 27.7 GB/s vs the doc's 63–70 GB/s

`devices/strix-halo-unified-memory.md` records `hipMemcpy H2D / D2H = 76–82 / 63–70 GB/s`.
The loader's copy-back measures 18–28 GB/s. **The doc is probably right and my number is a
different quantity.** The old claim comes from `tools/bw_probe_hip.cpp:155-166`: *one* bulk
`hipMemcpy` of the whole buffer into a pinned host allocation, best-of-N, on a quiet box.
Mine is 335 chunked copies (64 B … 485 MiB) with a `hipDeviceSynchronize()` after each, at
95–99 % util. The arithmetic fits that reading: at 63 GB/s the bytes need 24.5 ms, the
measured 55.8 ms leaves ~31 ms over 335 syncs ≈ 93 µs per sync — and the same window is
where H2D steady still reached 76.7 GB/s, i.e. H2D at spec and D2H at 2.3× below it is hard
to blame on the bus. What would settle it: a chunked-vs-bulk D2H sweep (same total bytes,
(a) one transfer, (b) the loader's 335 chunks with a sync each, (c) 335 chunks with one
sync at the end) at util ≈ 0 and util ≈ 98 %. If (c) ≈ (a) and (b) is ~2× slower, it is the
per-copy sync and the doc's row should be labelled "bulk, per-transfer"; if (a) falls with
util, the row needs a contention caveat instead.

Two notes for whoever runs it: the loader's D2H does **not** need to be fast (verification is
one-time and off by default), and dropping the per-copy sync would change the timing
instrument, not the guarantee — the verify pass would still hash every byte.

# W5b on disk: `state.{h,cpp}` + the launcher layer — proven, deferred, open

Everything in this section is **compiled, never run on a device**. No allocation has happened, so
no number here is a measurement of anything except the compiler's willingness.

## Proven on CPU

* `state_sizes.py` re-derives §08.1's shapes from `state.h`'s own constants and reproduces §00.5's
  rows (18.0 MiB GDN `S`, 12288 B/token KV). PASS.
* §04.5's gated RMSNorm is bit-exact against the pins on `dec8` (144 cases / 294 912 elements,
  ndiff 0) by the CPU mirror in `prototype/gdn_gated_norm/`, and so is `specimpl.rmsnorm_gated`
  called the way speccheck calls it (BF16 weight). That is the only new arithmetic this phase
  committed to, and it is the one the engine will call.

## Deferred, with the price named

1. **Unpacked projections.** `proj_gemv` is called once per projection (q, k, v, o, in_proj_qkv,
   in_proj_z, in_proj_b, in_proj_a, out_proj…) rather than through the packed multi-weight form the
   kernel supports. ≈358 launches/token instead of ≈225; at the ≈1.85 µs/launch floor
   (`tools/launch_overhead_hip.cpp`) that is ≈0.25 ms/token of pure launch cost, ≈0.12 ms of it
   removable by packing. Deferred because packing changes the buffer plan in `decode_step`, and
   `decode_step` does not exist yet.
2. **Dtype adapters: ≈66 cast launches/token.** `mlp_gemv` and `gdn_decode`'s conv/gates/rec take
   F32 activations, while `glue`/`proj_gemv` produce BF16, so the engine widens (48 of the 66 are
   the MLP's `x`, and E2's `PACK_X=false` adds ≈48 more for the projections' `x`).
   `cast_bf16_to_f32`, `cast_f32_to_bf16` and `cast_bf16_to_f32_3` are **declared** for exactly this
   reason (`kernels.h:82-91`) and **not written** — `kernels_cast.cpp` is in README's "Not written"
   list, so nothing currently folds three regions into one launch and this whole deferral rests on
   code that does not exist yet. The real fix is a BF16-staged form of `mlp_gateup`/`mlp_down` —
   `proj_gemv` proved that is bit-identical for a dot product — which would delete most of the 66.
   Not done: it means touching a graduated kernel and re-gating it, and `mlp_gemv`'s gate belongs to
   another phase.

Both deferrals are launch-count, not bandwidth: at ≈240 GB/s the token's memory floor is well under
1 ms and 358 launches is ≈0.66 ms, so they are the first thing a perf pass should attack — after
the token matches.

## Open questions this phase did not decide

* **Conv window dtype.** `state.h` stores it F32 (1.266 MiB) where §08.1's cell says BF16 (0.633
  MiB), because the graduated `gdn_decode` conv kernel takes F32 in and out and 36 cast launches
  per token is the wrong price for 0.6 MiB on a device using 4 % of its pool. The stored *values*
  are BF16-exact either way. §08.1 has **not** been corrected; the doc still contradicts the code.
* **§08.1 / §00.5 doc slips, unfixed** (found by `state_sizes.py`, listed in its OPEN lines): the
  "4 KiB/token/layer" KV cell contradicts the same table's 12 KiB/token total (2 KiB/layer is
  right); §00.5's 3.07 GiB at full context is 3.00 GiB from its own 12288 B/token. KV layout is
  head-major `[head][slot][dim]` per the kernel, not §08.5's `[slots][2][256]`.
* **§04.5 / A-01 still state the affine in F32** in `specification/`, and that is a reading the
  pins refuse: with the weight rounded to BF16 and widened back to F32 it misses 74 860 of 294 912
  elements, with the raw F32 checkpoint weight 105 683 (`prototype/gdn_gated_norm/results.md` §1).
  `speccheck.specimpl.rmsnorm_gated` is **not** among those: called the way speccheck calls it it
  is bit-exact, 0 of 294 912, because `Weights` hands it a BF16 weight. An earlier revision of this
  file reported the oracle as 105 683 elements off — that was the mirror probe handing the oracle
  an F32-widened weight, retracted in `fc444d0`, and the probe now asserts its oracle row at 0.
  Correcting the spec wording is a decision for the spec owner, not this phase.
* **`lm_head` full + host argmax**, not the fused single-kernel form: the fused form resolves ties
  to the highest id and §03.4 fixes ties to the lowest. Costs ≈1 MB D2H + a host scan (≈0.04 ms)
  per token and gives the gate its logits. Worth revisiting only with a tie-corrected fused kernel.
