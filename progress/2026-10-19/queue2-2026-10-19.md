## Item R — phase-by-phase regression check: HEAD vs `origin/master`

**What the baseline actually is.** `origin/master` = `9303c13`, HEAD is **28 commits ahead and 0 behind**
(verified `git rev-list --count HEAD..origin/master` = 0), so the baseline is the tree just before the
WMMA attention round: it contains the looped GDN launch (§23–§25), the conv coalesced read, the gate
fixes, and `attn_slim_wave` as the only attention form; it lacks §29–§33 entirely.

**Decision R1 — compare *families*, not just totals.** The round changed attention and the launcher's
row-block rule; the risk is not that `attn` got slower (measured: 1.985× faster) but that something
**outside** it moved: `attn_slim_wave`'s one-pass rows, the split/combine launches, casts, and the
`FATTN_ROWS_PER_BLOCK` change that §34 shows was easy to half-commit. A total-only comparison would
hide exactly the regression most likely to exist.

**Decision R2 — paired in one window, not two.** §6's bimodality and §36's re-take both proved that a
ruler re-taken in a different window is not an A/B. So both binaries run **inside one lock hold,
alternating per rep**, medians of 3, at the widths the ledger uses (4,096 ruler + 1,024 pair).
Baseline built in a scratch `git worktree` (never in the working tree) with `engine/build.sh`, which
takes 17.4 s per tree.

**Decision R3 — a behavioural canary inside the window, per the D30 rule.** A stale-binary A/B reads as
a clean null. The canary is `--attn-fattn`: the baseline **must fail or refuse** the flag (it predates
it) and the HEAD side must print `ATTN_FATTN`; and the family line for `attn` must differ between sides
by more than noise, or the window is discarded rather than reported.

**Decision R4 — numerics at the same time, cheaply.** `gate.py` on `wide520f` and `wide1024f` for the
baseline binary, which is the admission the round was gated on, so a red there is a regression claim
rather than an inference. No full 26-gate sweep: budget verification to what changed (§standing rule).

**Deliverable:** `bench/performance-status.md` §37 with a family table (baseline / HEAD / ratio, per
width), the canary's evidence, the numerics verdict, and an explicit "what this cannot see" line.
Harness: `tools/regress_vs_origin.sh`, committed, so the check is re-runnable at any later tip.

## Item L — longer context than 4,096

**What the wall actually is (audited, not guessed).** Three separate things, and only two are real:

| limit | value | is it a wall? |
|---|---|---|
| `engine/decode_run.cpp:64 kSessionDefaultCap` | 4,096 | **not a wall** — a default, `--session-cap`-shaped already? (to confirm) |
| `engine/decode_step.h:51 kMaxWaveRows` | 512 | a wave-row ceiling; §17's note: the **lane ceiling is `MAXSC × kAttnMaxSplit` = 512 × 9 = 4,608**, so this is the real wall today |
| `engine/kernels_attn.cpp:68 kAttnMaxSplit` | 9 | raising it is what §17 called "a long-context enabler, not a speed item" |

Capacity is not the problem and this is the case the scope note in `AGENTS.md` was written for: 12 KiB/token
of KV means 32,768 lanes cost **384 MiB**, against a ~34 GiB pool; per-request state is 18.66 MiB and does
not grow with context. So long context is an **arithmetic and index-width question, not a memory question**
— which is precisely what the light test has to witness rather than assume (int32 index overflow starts at
2^31 bytes of a buffer, and `2·4096·4` per-row strides at 32k rows are where that bites first).

**Decision L1 — raise the ceiling by split, not by making `MAXSC` bigger.** `MAXSC` is the shared-memory
score stage (`attn_slim_wave` stages one block's scores), so it is LDS-bound and stays; split is the lever
the geometry already supports (§17's row). Raise `kAttnMaxSplit` and pin the arithmetic in the test.

**Decision L2 — "seems all-right" is a defined set of checks, not a vibe.** The operator asked for light but
**reproducible**. The committed check asserts, at each of 8,192 / 16,384 / 32,768 lanes: the run finishes;
every logit finite; `plan_match=1` and the launch counts equal the plan; the KV/state buffers grew to the
booked size (no silent clamp); and **prefix consistency** — the logits at row *N* of a long prompt equal the
logits at row *N* of the truncated same prompt, which is the one property that would catch a wrong index
where a finite-value check cannot. No HF pins exist at those widths, so no band is claimed and none is faked.

**Decision L3 — cost is stated, not hidden.** Quadratic attention means 32k prefill is not 8× 4k; the test
reports the measured shape so a future reader is not surprised, and the ledger says explicitly that long
context is enabled, not optimised.
