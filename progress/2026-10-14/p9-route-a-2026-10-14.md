## 1. The arithmetic before the kernel

`.venv/bin/python prototype/gdn_collapse/collapse_price.py --geometry` prints all of this; it imports its
anchors from `prototype/gdn_chunk/kernel_price.py` (which carries the file each number was measured in)
rather than retyping them. The short version:

* **Grid.** 36 (layer, body) sites per 1024-lane wave (18 GDN layers × 2 bodies of 512). One launch per
  site, `dim3(4 strips, 16 heads)` = 64 blocks of 128 threads. Against `40 CUs / 160 SIMDs` that is
  **2,048 useful lanes of 5,120 = 40 %**. That is not a staging shortfall and no re-blocking fixes it:
  §04.4's scan has exactly `16 heads × 128 d_v columns = 2,048` independent chains, full stop. The rest
  of the occupancy picture is worse than that number suggests — 192 of the 256 wavefronts32 per site
  exist only so the norm reduction can run at the shipped width (§2).
* **Work per token per useful wavefront: 1,370 instructions** (768 LDS, 602 VALU). One issue slot per
  SIMD per cycle → 1,370 cycles/token → 512 tokens serial per site → 318 µs/site → **11.4 ms per
  1024-lane wave**, and 34.3 ms at 3072 lanes (6 bodies).
* **Cross-checked as a rate.** 33.94 GFLOP / 11.4 ms = **2.96 TF/s**, which sits on the fp32 vector row
  (2.93 TF/s, `devices/strix-halo-compute.md`) rather than above it — the estimate is not claiming a
  physically impossible rate. The same work at the engine's best hand-GEMM rate (0.85 TF/s) is 40 ms;
  at the chunked kernel's *executed* rate (0.417 TF/s) it is 81 ms, i.e. **over the line** — and the
  reason that rate does not transfer is its own instruction mix: 3 VALU + 1 LDS per MAC, a BF16 rounding
  ladder on every operand, and 13.5× the priced arithmetic re-executed
  (`prototype/gdn_chunk/kernel_price.py`). Route A's inner loop is 1 LDS + 1 FMA per MAC with no
  rounding at all; `--isa` (§3) is the census that says so, and `s_v_mfma` count is zero.
* **Traffic, which is what the route actually removes.** Sequential: `S` traverses memory twice per
  token per layer = 38.7 GB per wave = 42 ms at the L2-resident rate, 163 ms if DRAM-cold. That is where
  the 127 ms went. Resident: 75 MB per wave = **0.08 ms**. Cost paid instead: q|k|v is re-read once per
  strip (4×) because each strip recomputes the norm rather than sharing it — 1.36 GB, 1.5 ms at L2 rate,
  5.7 ms cold. Bytes per useful flop: 0.0022 (state) / 0.040 (counting the redundant operand reads).
* **Dispatch**: 36 launches vs 18,432 → 33.1 ms of the 1.8 µs/launch floor removed.

**Verdict recorded before the kernel was written:** bottom-up 11.4 ms, double that is 23 ms, so the route
clears the 63 ms line on the bottom-up model and on the hand-GEMM rate, and fails only on the chunked
kernel's executed rate, which the instruction census says is the wrong yardstick for this shape. D-12's
own band (40–80 ms) bracketed that disagreement; the arithmetic said proceed, so the kernel got written,
and the line is unchanged: **if the device lands above 63 ms the route is dead whatever this file said.**

## 2. What was built, what was shrunk, and what it cost

`engine/gdn_collapse_kernels.h` (kernel) + `engine/kernels_gdn.cpp::gdn_rec_collapse` (launcher) +
`--gdn-scan collapse` through `engine/decode_step.cpp`.

* **Bit identity is a construction, not a measurement.** The per-step expressions, the two ascending `i`
  loops, and the ascending order are the shipped `rec_kernel`'s, verbatim; the state round trip through
  LDS is F32 in and F32 out, which is exact. The one non-trivial choice is the norm reduction: rather
  than re-derive a 32-lane equivalent of `rec_kernel`'s 128-thread `block_sum` tree — which would hang
  the identity on how this device fills an out-of-range `__shfl_down` source lane, an undocumented thing
  to bet a gate on — the collapsed kernel **keeps `blockDim.x == 128` and calls the same `block_sum`**,
  fed the same element-per-thread mapping.
* **The cost of that choice, named:** three of each block's four wavefronts exist only to widen the norm
  tree and park at its barriers; warp 0 alone drives the recurrence (one thread per `d_v` column, which
  is what preserves the per-column serial `i` order). That is ~90 instructions of redundant norm work per
  token per strip block and 192 parked wavefronts per site.
* **What got shrunk to hit ≥ 2 blocks/CU: the strip, from 64 columns to 32.** LDS is 17,424 B/block
  (128×32 F32 state = 16,384 + k̃/q̃ staging 1,024 + 4 reduction partials) → **3 blocks/CU** against
  65,536. A 64-column strip is 33,808 B = 1 block/CU, because the state alone eats the whole LDS budget
  before the k̃/q̃ staging is added — so 64 was never an option, not a knob that was turned down. The cost
  of 32: q, k and v are re-read by each of the 4 strips of a head (the 1.36 GB above), and the norm tree
  runs 4× per (token, head). `slot()` swizzles banks (`c ^ (i & 31)`) instead of padding, which is what
  keeps it at 3 blocks/CU rather than 2.
* **Occupancy, stated honestly:** the *capacity* is 3 blocks/CU (requirement met with headroom); the
  *realised* fill from a 64-block grid over 40 CUs is 1.6 blocks/CU and 40 % of FP32 lanes doing work.
  The route buys its win by removing launches and state traffic, not by occupying more of the machine —
  and §04.4's serial width is why it cannot occupy more.
* **Per-token barrier removed** (was one per token in the first draft): `block_sum` already fences
  `ks`/`qs` with four barriers per call, and each lane's state columns are private to it. The barrier
  that *is* required is the one before the write-back — warps 1..3 leave the token loop as soon as the
  last reduction returns, and would otherwise read state cells warp 0 is still writing.
* **`gdn_chunk` now fails closed** (§1c.1 D6: the carry formed the chunk-boundary decay as `gamC/gam[i]`,
  which underflows to NaN where the contract uses one `exp` of a difference). `parse_gdn_scan("chunk")`
  refuses with the reason and points at the record; `engine/gate.py --gdn-scan` no longer offers it. The
  kernel, `phase1.py` and `kernel_price.py` stay in the tree so the route can be re-funded rather than
  reconstructed. This is its own commit.
* **Fail-closed negatives**, as compile-time `-D` builds (never a runtime branch, so a defect cannot be
  reachable from the shipping binary): `NEG_RC_STATE_BF16` (state rounded on staging), `NEG_RC_STRIP_SHIFT`
  (column base taken from the head index), `NEG_RC_NORM_HALF` (reduction fed half the elements),
  `NEG_RC_I_DESC` (step-2 dot walked downwards). All four compile (checked by `--isa`), and all four are
  caught by the CPU mirror (§4).

## 4. The CPU bit-identity proof

`.venv/bin/python prototype/gdn_collapse/collapse_mirror.py --selftest` — mirrors `rec_kernel`'s order
and the collapsed order as two separate programs over the same operands and the same starting state, and
compares `o` and the resulting `S` **bit for bit** (uint32 view, not a band).

```
block_sum model: two independent implementations agree bit-for-bit on 40 rows; worst gap to a plain
F32 sum 1.77e-07 (association, as expected — that is why the collapsed kernel reuses the same function)
operands: p300/L00 gdn q|k|v post-conv + g_decay_log + beta, 277 pinned rows

== rows=277 state=zeros
   o bit-diff 0/567296   S bit-diff 0/262144   [0.5s]
   BIT-IDENTICAL: every element of o and of the resulting state is the same bit
   pinned witness (mirror vs HF: expected close, not bit-exact — §10.1) o cos=0.999998638
   max_abs=9.710e-04 | state cos=1.000000000 max_abs=2.146e-06
== rows=1024 state=zeros  (synthetic-wide: pinned rows tiled to lengthen the body)
   o bit-diff 0/2097152   S bit-diff 0/262144   [2.0s]   BIT-IDENTICAL
== rows=277 state=random  / == rows=1024 state=random    BIT-IDENTICAL (both)

== negatives and controls (48 tokens, carried non-zero starting state)
   [CAUGHT ] state_bf16  o 77062/98304  S 196489/262144   state rounded to BF16 on the way into LDS
   [CAUGHT ] strip_shift o 73728/98304  S 196608/262144   strip column base taken from the head index
   [CAUGHT ] norm_half   o 98304/98304  S 261248/262144   norm reduction fed half of the squared elements
   [CAUGHT ] i_desc      o 55335/98304  S 147902/262144   step-2 dot walked with i descending
   [CAUGHT ] fused_loop  o 98300/98304  S 261247/262144   read and update fused into one pass
   [CAUGHT ] gam_hoist   o 96256/98304  S 261248/262144   gam/beta hoisted out of the token loop
   [CLEAN  ] strips_rev  o 0/98304      S 0/262144        strips processed in the other order
   [CLEAN  ] body_split  o 0/98304      S 0/262144        body split in two, state handed between halves
SELFTEST PASS
```

Three things about this proof that have to travel with it:

1. **The operands are `p300`'s pinned L00 tensors, not `wide1024f`'s.** `wide1024f` carries no per-layer
   GDN operands (`L00.gdn.q_post_conv.npy` and friends are not in it — checked), so there is nothing
   there to run a single layer's recurrence on. The mirror therefore uses real pinned post-conv q|k|v,
   `g_decay_log` and `beta` from `p300`, and gets its *length* by tiling those rows to 1024, labelled
   `synthetic-wide` in every line of output. The device gate is the thing that runs on `wide1024f`
   itself, end to end, which is where a 1024-lane claim actually lives.
2. **The sequential side is witnessed against the pinned HF dumps** (`state_new`, `o_pre_norm`) before
   the two mirrors are compared with each other — close, not bit-exact, as §10.1 requires of an F32 chain
   vs HF's own. Without that the mirror could be agreeing with itself about the wrong recurrence, which
   is the §10.5 hook-output trap.
3. **What a CPU mirror cannot see**: FMA contraction and the device intrinsics. Those rest on the kernel
   using the shipped source expressions (and on §3's census), and ultimately on the device byte-comparison
   in §5. And one derived lesson, same shape as the AGENTS trap about hand-listed must-catch sets: the
   `state_bf16` negative is **invisible from a zero starting state** — staging a rounded zero is still
   zero — so the mirror runs its negatives from a carried non-zero state, and the device negative must
   be run on a wave with **more than one body** (≥ 2 bodies at 1024 lanes ✓), where the second body stages
   the first one's state.

## 6. Status, and what is *not* claimed here

Built and CPU-proven: kernel, launcher, `--gdn-scan collapse`, the `gdn_chunk` refusal, the CPU mirror with
its negatives and controls, and the geometry arithmetic with the compiler's resource read next to it.
**Not claimed**: any millisecond figure; the 11.4 ms of §1 is an arithmetic projection, and if the device
disagrees the device is right. **Not done**: no `LAUNCHSTATS` family for the recurrence (deliberate, and
the reason is in `kernels_gdn.cpp`), no change to `speccheck/` (the route does not move the reference), and

forgets to set `gdn_resident` shows up as a plan/count mismatch rather than as a plausible wrong share.

## Parent's device window (2026-10-14, locks `ROUTE-A`/`RA2`): **collapse faults on device — it does not ship**

`--gdn-scan collapse` dies in the first body with a GPU memory fault:

```
Memory Fault Error [..., faulting addr: 0x776f53e00000]
decode_run FAILED: hip: an illegal memory access was encountered at engine/decode_step.cpp:
    hipMemcpy(host_logits.data(), sc.logits, kVocab * sizeof(float), ...)
```

and the `--time-waves` run produced no `WAVEPASS`/`gdn_rec` line at all, so **there is no route-A timing** — the
comparison table stays `seq` = **123.8 ms / 37.31 % of a 331.7 ms wave** (18,432 launches at 6.71 µs), with
`collapse` blank.

Two things I want on the record because they are how this gets fixed rather than repeated.

**I nearly mis-read my own check.** The byte-identity diff reported `DIFF logits1023.bin / logits1024.bin /
sampled.txt`, which is exactly the shape of the §17 false alarm: the collapse run threw before writing anything, its
`sampled.txt` is **0 lines**, and `cmp` called missing output a numerics difference. The correct reading is
"the run never produced results", not "collapse differs by one row" — and the tell is always the row count, never
the diff list.

**The suspected shape, stated as a question for the next pass, not an answer.** The kernel is billed as grid `(4,16)`
× 128 threads with one head's 32 `d_v` columns of F32 state resident in LDS at 17,426 B/block; the fault address is
a global, not an LDS offset, and the fault surfaced at the `sc.logits` copy — so the leading candidates are a
global staging index that runs past its array for the last head or the last body (grid `(4,16)` against
`heads × bodies` arithmetic), or a launch configuration mismatch between the billed geometry and what the kernel
actually indexes. CPU mirror cannot catch this class — it is device-resident geometry, which is exactly why the
hand-off had to be run before anything was believed.

**Status of D-12's funding question: RESOLVED, and the route is dead.** The kernel was repaired (two
device-side defects: the staging/write-back loops indexed a 32-column strip with `tid` over 128 columns,
which read and wrote up to 96 floats past every head's state and 65 cells past the end of its LDS array;
and `q̃` was written as `qv * (rsqrtf(·) * Q_SCALE)` where the shipped kernel computes
`(qv * rsqrtf(·)) * Q_SCALE`, which moved 93,522 of 131,072 `o` elements while leaving the state
bit-exact). With both fixed the form is **bit-identical to `seq` on all ten fixtures end-to-end**
(`wide1024f`: 4,132 files, `diff_lines=0`), which is D-12's arithmetic case vindicated — and it measures
**112.04 ms best-of-3 against the 63 ms win line and the 84 ms kill line**, so D-12's own rule kills it.
The end-to-end prize was 6.8 ms on a 322 ms wave. Full verdict, including why the 11.4 ms bottom-up
projection was 9.8× wrong and what that says about the recurrence itself, is in
`prototype/gdn_collapse/results.md` §4–§5 and in `bench/performance-status.md` ("Route A … killed by its
own line"). `--gdn-scan` keeps `seq` as the default; `collapse` remains selectable and is not
failed-closed, it is simply not a win. `seq` remains the shipped form and the honest headline is
unchanged at 2,706 prompt tok/s @1024; the chunked route stays failed-closed.
