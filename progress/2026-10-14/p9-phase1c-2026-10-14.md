# P9 Phase 1c (2026-10-14, CPU-only): the named defect, the price of the 5.9×, and the decision

Phase 1b (`progress/2026-10-14/p9-phase1-2026-10-14.md`, "Phase 1b device window") left two open questions and one
decision:

* **Q1** — why is `gdn_chunk_carry` right for chunk 0 and NaN for every later chunk? Named line +
  failing CPU reproducer, not a hypothesis.
* **Q2** — *price* the 5.9× slowdown (331.2 ms → 1953.7 ms wave; `gdn_rec` 127.0 ms → ~1750 ms),
  against 40 CUs, blocks/CU from LDS, waves in flight, bytes per useful work. Attribute the added
  1,622 ms. State the best case for that geometry.
* **Q3** — a decision: a redesign with arithmetic showing `gdn_rec` ≤ 63 ms, or **kill P9** and name
  another route to the 127 ms / 38.35 % line.

**Nothing in this file is a device measurement.** No kernel was launched, no timing was taken, no
number here may enter `engine/performance-status.md`. Q2 is arithmetic on numbers already measured in
`devices/` and `bench/`, plus a compile-only `hipcc -c --offload-arch=gfx1151` (a cross-compile; the
device is untouched). The device commands the parent needs are §1c.4.

Answers up front:

1. **Q1 — one line, `prototype/gdn_chunk/gdn_chunk_kernels.h:263`.** The kernel forms the boundary
   decay as `gamC / gam[i]` — two `expf`s and a division — where the CPU contract forms it as one
   `exp` of a difference. `expf` underflows to 0 below about −104 in F32, the real gate cumsums
   reach −293, so the division is `0/0 = NaN`; `khat` is read only by the state update, so the
   damage lands in the state the *next* chunk inherits. That is the whole signature: chunk 0's rows
   correct, every row of every later chunk NaN. `prototype/gdn_chunk/kernel_mirror.py` reproduces it
   on the pinned operands and `chunk_scan.py` does not. It is **not** one of D1–D5; it is an unlisted
   deviation, now recorded as **D6**.
2. **Q2 — the added 1,622 ms is ~99 % duplicated arithmetic, and both of Phase 1b's hypotheses were
   wrong about it.** `const int jl = tid & (GC_STRIP - 1);` at `gdn_chunk_kernels.h:379` is
   *declared and never read* — the compiler says so: `warning: unused variable 'jl'`. The thread
   mapping the carry's own header comment claims (`thread = (chunk row t, strip column j)`) is not
   the one in the code: every lane of a row-group computes all 32 strip columns of `v_new` and `out`,
   so the executed carry is **24.3×** the modelled carry and the executed wave is **730.4 GFLOP
   against the 54.03 GFLOP Phase 0 priced — 13.5×**. At the two hand-loop rates this box has
   actually measured (0.267 and 0.85 TF/s) that spans 859–2,733 ms, which contains the measured
   ~1,750 ms. Serialised carry ≈ 4 %, LDS occupancy ≈ ≤10 % and not separable, launch count is a
   **credit** (+33 ms saved), duplicated work ≈ 99 %. Best case for the geometry, after both fixes:
   **63.6 ms at the engine's best hand-GEMM rate and 18.4 ms at the fp32 vector ceiling** — i.e. the
   ≤63 ms win line needs 0.858 TF/s = 101 % of the best hand loop this engine has ever produced, and
   the kernel as built runs at 0.417 TF/s **on the work it actually does**, which is below Phase 0's
   own break-even rate of 0.431 TF/s.
3. **Q3 — kill the chunked scan.** Recommendation with alternatives priced: §1c.3. The kill is not
   "chunking is wrong"; it is "this geometry, on the vector path, needs a rate this engine has never
   sustained, and the sequential line's remaining 127 ms is 58 % overhead that a cheaper kernel
   removes without changing a single bit".

## 1c.1 Q1 — the named line, and the reproducer that fails on it

### The one expression

`prototype/gdn_chunk/gdn_chunk_kernels.h:263`, in `gdn_chunk_prep`'s normalise loop:

```c
    if (tid < GC_C) gam[tid] = expf(cum[tid]);            // :235   gam[t] = exp(cum_t)
    const float gamC = gam[GC_C - 1];                     // :237   Gamma_C = exp(cum_{C-1})
    ...
    a.qg[off] = hip_bfloat16(qq * qr * GC_QSCALE * gam[i]);              // :262  one exp, fine
    a.kh[off] = hip_bfloat16(kq * kr * (gamC / gam[i]));                  // :263  TWO exps, divided
```

`prototype/gdn_chunk/chunk_scan.py:196`, the line the contract prices:

```python
    k = k * (cum[..., -1:] - cum).exp()[..., None]        # one exp of a difference, always in (0, 1]
```

They are the same number in exact arithmetic and different numbers in F32. Because every gate is
negative, `cum` is monotonically decreasing, so `cum[C-1] ≤ cum[i]` and `gamC ≤ gam[i]`: the two
exps underflow **together**, and the quotient is then `0/0`, not `inf`. The model's form has no
intermediate to underflow — it underflows only where the *true* ratio underflows, and there the
answer is 0, which is the right limit (a token 293 nats back contributes nothing).

The condition is per (chunk, head), not per row: `khat` is NaN for **every** row of a chunk whose
`cum[C-1]` passes the threshold, including rows whose true ratio is exactly 1.0. From the probe
output, real examples on pinned gates:

| layer / chunk / row / head | `cum_t` | `cum_last` | kernel `gamC/gam[t]` | model `exp(cum_last − cum_t)` |
|---|---|---|---|---|
| L00 c0 r45 h13 | −105.21 | −105.21 | **NaN** | **1.0** (exactly 1 — it is the chunk's last row) |
| L02 c0 r61 h0 | −105.21 | −111.94 | **NaN** | 1.198e-3 |
| L04 c0 r61 h1 | −105.92 | −110.86 | **NaN** | 7.189e-3 |
| L00 c0 r27 h0 | −107.34 | −243.27 | **NaN** | 0.0 (the honest underflow) |

Row 2 of that table is the point: the destroyed ratio is 1.2e-3, not a denormal. The underflow
threshold is −103.98 for F32 `expf`; −87.3 if the device flushes denormals to zero. The real gate
cumsums are at −61.4 (dec8), −163.3 (p64) and −293.7 (p300), so the conclusion is insensitive to
which of the two thresholds the device actually uses.

`khat`'s only reader is the state update (`S = cdec·S + khat^T @ v_new`, `gdn_chunk_kernels.h:468`),
which runs at the *end* of a chunk. So a poisoned chunk writes a poisoned state and keeps its own
output rows clean. That is the observed signature, and it is why Phase 1b's split read the way it
did:

* `dec8` (17 tokens, 1 chunk, worst cumsum −61.4): cannot reach the threshold at all → PASSES.
* `p64` (46 tokens, 1 chunk, worst −163.3): **is** poisoned — 4 of 288 chunk-heads underflow, 184
  NaN staging entries, 114,688 NaN state elements — and still has no *output* row to be wrong in,
  because there is no later chunk. A one-chunk fixture cannot observe this defect even when it has it.
* `p300` (277 tokens, 5 chunks, worst −293.7): 21 of 1,440 chunk-heads underflow, and the first
  poisoned one is layer 0 chunk 0 → first NaN output row 64.

### Why that is the first answer token, not merely a wrong one

`tmp/gdn/w1024chunk/logits<i>.bin` is one F32 logits row per prefill row, 1,032 of them. Reading
them back (`kernel_mirror.py device`):

```
=== device run tmp/gdn/w1024chunk: 1032 prefill rows, 17 chunks of 64
    first row with a non-finite logit: row 64, which is the start of chunk 1
    per-chunk all-NaN pattern: .NNNNNNNNNNNNNNNN   (N = every row of that chunk is NaN)
```

The row that decides the first answer token is the last prefill row, 1031, and it is all-NaN. The
engine's argmax takes ties to the LOWEST id by a strict `>` (`engine/decode_step.h:178`), and every
comparison against NaN is false, so the running maximum never moves and **token id 0 wins**. That is
Phase 1b's `first answer token 0 where the pin says 279` — the `0` is not a token, it is the absence
of a comparison. (Inference about the argmax's semantics, stated as such; it is checkable with the
one-line CPU check in §1c.4.)

### The reproducer

`prototype/gdn_chunk/kernel_mirror.py` — a CPU mirror of the **kernel as written**, the way
`prototype/attn_tile_model.py` is a mirror for the tiled attention core. It keeps the kernel's
staging dtypes and rounding points (BF16 `k~` in LDS and the three quantities derived from it, i.e.
D2's double rounding; `U` F32 in LDS and BF16 at use; `intra`/`kcd`/`qg`/`kh` rounded at the store;
`nv`/`v_new` F32 results rounded at each use; the state read as a BF16 operand and written F32), the
within-chunk cumsum order, the row-ascending unit-triangular substitution with row 0's seed (the
`59c43dc` fix), the chunk-boundary conditions and §04.7's ragged-tail padding. It does **not** mirror
D1 (the F32 association inside a dot — no CPU form can be both), so every verdict here is a
finiteness or budget verdict and never bit-identity, per §10.1 (F1–F4). `--selftest` = 0 failures; it
asserts the two facts the finding rests on (that line 263 still divides two exps, and that the
mirror's kernel-form path is the one that goes non-finite).

```

    form                                  first NaN o row  NaN o rows  NaN state elems
```

Row 64 on p300 is the device's row 64, from independent operands: the mirror was run on the pinned

### The bisection: four candidates, one discriminator each

`kernel_mirror.py candidates --fixture p300` adds each candidate mechanism on top of the *finite*
baseline, so a candidate cannot hide behind the defect. The device signature to match is
(chunk 0 damage = 0, chunk ≥ 1 damage = non-finite):

```
    mechanism             non-finite     chunk 0   chunk >=1  reading
    baseline (fixed)               0    0.00e+00    0.00e+00  finite everywhere; what the fix must give
    carry_seed                     0    0.00e+00    4.36e-01  chunk i reads the state as of the body start
    bound_head                     0    0.00e+00    8.27e-01  the boundary update reads head h+1
    ut_no_seed                     0    3.84e-01    3.91e-01  U row 0 uninitialised (pre-59c43dc)
    strip_global                   0    0.00e+00    0.00e+00  state strip via global, not LDS
    ut_no_decay                    0    7.86e-02    8.57e-02  GCK_UT_NO_DECAY, a known-loud control
    gamC/gam (THE LINE)       742016    0.00e+00    9.74e-05  khat from two exps and a division
```

Read against the brief's four candidates:

| candidate | verdict | why |
|---|---|---|
| carry seeding | **excluded** | localises to chunk ≥1 exactly as the device does, but produces *finite* numbers (4.36e-1 damage). The device returned non-finite. |
| boundary indices | **excluded** | same: right locality, wrong kind (finite, 8.27e-1). |
| unit-triangular solve's chunk-0 case | **excluded** | `ut_no_seed` and `ut_no_decay` both damage **chunk 0** (3.8e-1, 7.9e-2). The device's chunk 0 is clean. |
| state-strip residency | **excluded, and untestable this way** | `strip_global` is arithmetically a no-op: residency moves bytes, not values. LDS sizing, block geometry and the thread mapping cannot produce a NaN. |
| **`gamC / gam[i]`, :263** | **the mechanism** | the only non-finite path (742,016 non-finite output elements), and the only one that leaves chunk 0 untouched. |

Two discriminators did the work — finiteness, and chunk-0 cleanliness — and both had to be derived
from the geometry rather than hand-listed, which is the lesson already in `AGENTS.md`'s traps table
(the `attn_tile_model.py` negative-set lesson).

### The fix, and what it does not buy

```c
-            a.kh[off] = hip_bfloat16(kq * kr * (gamC / gam[i]));
+            a.kh[off] = hip_bfloat16(kq * kr * expf(cum[GC_C - 1] - cum[i]));
```

The model's expression, one `exp` of a difference. Post-fix budget verdict on p300 (`budget`):
`o_pre_norm` meanrel vs the pin **4.237e-3** against the 9.9e-3 budget (the contract itself is
3.975e-3), `state_new` 3.433e-3, worst per-layer 1-cos 6.285e-6 against the 3.2e-4 row budget, and
`non-finite o elements: kernel form 463488, fixed form 0`. Mirror-vs-contract o meanrel is 3.696e-3,
which is D1's association floor, not an error.

What the fix does **not** buy: it makes the kernel compute what `chunk_scan.py` prices. It does not
touch the cost problem (§1c.2), and it has not been run on a device — see §1c.4. It is recorded as
**D6** in the header, comment-only; this pass changed no code, because the decision it belongs to
(§1c.3) is the parent's.

## 1c.2 Q2 — the price of the 5.9×, on paper

`prototype/gdn_chunk/kernel_price.py` recomputes every number in this section; `selftest` asserts the
compiler resources it quotes (so the occupancy argument cannot rot), that no `v_mfma` appeared, that
the modelled work still reproduces Phase 0's 54.03 GFLOP, and that `jl` is still unread.

### The geometry, from the compiler rather than from the comment

Compile-only (`hipcc -O3 --offload-arch=gfx1151 -c`, `--save-temps`), 40 physical CUs
(`devices/strix-halo-compute.md`; HIP's "20" is wrong), 65,536 B LDS per CU, 32 waves per CU,
2.206 GHz:

| | `gdn_chunk_prep` | `gdn_chunk_carry` |
|---|---|---|
| VGPRs / SGPRs / scratch | 35 / 44 / 0 | 79 / 72 / 0 |
| register-limited occupancy | 16 waves/SIMD | 16 waves/SIMD |
| **LDS per block** | **34,176 B** | **24,576 B** |
| **blocks per CU** | **1** (two would need 68,352 B, **2,816 B over**) | **2** |
| waves resident per CU | **4 of 32 = 12.5 %** | **8 of 32 = 25.0 %** |
| blocks per (layer, body) site | 8 chunks × 16 heads = 128 | (128/32) × 16 = 64 |
| blocks per 1024-token wave | 4,608 (115.2 per CU) | 2,304 (57.6 per CU) |
| residency rounds per site | 128 / (40×1) = **3.20** | 64 / (40×2) = 0.80 |
| static `s_barrier` sites | 21 | 5 |
| LDS instruction widths (sites) | `ds_load_b32` 24, `ds_store_b32` 14, `ds_load_u16` 5 — **no b64/b128 at all** | `ds_load_b32` 128, `ds_store_b32` 48, **`ds_load_b128` 16, `ds_store_b128` 24** |
| cross-lane sites | `ds_bpermute` 16, `ds_swizzle` 4 (= `gc_block_sum`'s `__shfl_down_sync` tree) | 0, 0 |
| BF16 round spellings | `v_cvt…bf` 11; the RNE ladder is `v_add_co_*` + `v_and_b32` | 0 cvt sites — the round is the software ladder inline |
| `v_mfma` sites | **0** | **0** |

Three things the census supports, and only these. **(1)** `prep` moves every LDS element through a
4-byte `ds_load_b32` — the shape of code that walks `d` serially per thread — while the `carry` does
vectorise (b128 sites) in its state staging and `vn` reads. **(2)** `prep`'s `[C,C]` loop: lane L
owns `p = tid + k·128`, so lanes differ in `s` and read `kst[s*GC_D + d]` at addresses `GC_D` = 128
words apart, and 128 words is four full turns of the 32 LDS banks — all 32 lanes land in **one**
bank, a 32-way conflict on a 4-byte read. The paired read `kst[t*GC_D + d]` is warp-uniform and
broadcasts free. So half of `prep`'s LDS reads are conflicted, worth **~14 ms**, and padding the
pitch to `GC_D+1` words takes it to ~0.5 ms: an indexing change, not an arithmetic one, and not the
story. In the `carry` the hot `S[i][j]` reads are broadcast-shaped too — with `jl` dead every lane of
a row-group reads the *same* word — so the carry has no bank conflict at all; its LDS term is ~2 ms
and its problem is purely the arithmetic behind those reads. **(3)** a BF16 round-trip on gfx1151 is
a software ladder (`v_add_co_*` + `v_and_b32` mask), not one instruction, so `gc_bf()` costs ~3 VALU
ops per element on top of the FMA that consumes it: every MAC in these kernels carries an LDS load
plus that ladder, which is the instruction-mix reason a hand loop here sits near 0.4 TF/s rather than
the 2.93 TF/s ceiling.

Phase 1b's second guess — "the LDS-resident state is throttling occupancy to nothing" — is *true and
second-order*. The register file would allow 16 waves/SIMD; LDS is the only reason the occupancy is
4 and 8 waves, and `prep` misses 2 blocks/CU by **2,816 B**. Shaving ~2.8 KiB (e.g. BF16 `intra`
staging, or the row-strip idea D2 already names as the next move) doubles `prep`'s residency for free.
But the whole of `prep`'s executed arithmetic is 25.0 GFLOP, which at the *worst* measured hand-loop
rate is 94 ms — so no occupancy story about `prep` can be worth more than a tenth of the 1,622 ms.

0 `v_mfma` in both kernels: this is a vector FMA path, so its ceiling is the fp32 row of
`devices/strix-halo-compute.md`, **2.93 TF/s**, and the engine's best hand-written GEMM is **0.85 TF/s**.

### Grid and launch shape — the part of the cost model that worked

```
serial depth per block: 8 chunk-steps (was 512 token-steps in gdn_rec); the carry is 8
                        dependent steps, each with 3 __syncthreads
launches: 72 replacing gdn_rec's 18,432 at the 1.8 us eager floor = 0.13 ms vs 33.2 ms
```

The launch-count win was real and is worth ~33 ms of dispatch; the serial-depth reduction (512 → 8)
was real too. Neither is visible next to +1,622 ms.

### The executed work, and the dead variable

`gdn_chunk_kernels.h:379`:

```c
    const int jl = tid & (GC_STRIP - 1);   // column inside the strip
```

That is the only occurrence of `jl` in the *code* — the header now quotes it in comments, and
`kernel_price.py selftest` strips comments before asserting the count, so the check cannot be
satisfied by prose. `hipcc -Wall` says it plainly:

```
prototype/gdn_chunk/gdn_chunk_kernels.h:379:15: warning: unused variable 'jl' [-Wunused-variable]
```

The carry's header comment promises `thread = (chunk row t, strip column j) … ≈2048 MACs per thread`.
The code is `for (t = tg; t < GC_C; t += tstep)` with `float acc[GC_STRIP]` — each thread walks
**all 32** columns, so every lane of a row-group recomputes the same 32 columns of `v_new` and of
`out` (and the `out` store is issued 32× to the same addresses). Intended ≈2,048 MACs/thread/loop;
as written 65,536. Only the state-update loop (`i = tid`, columns in registers) is mapped as
designed. The fix is the variable that is already declared: index the accumulator by `jl`, which
removes 32× of the arithmetic and 32× of the LDS *instructions* (today each lane issues all 32 reads
of a row as broadcasts, where one read per lane would do), and turns the per-lane `S[i][j]` read into
the contiguous wave32-distinct 128 B window the comment describes. Neither pattern conflicts today —
32 broadcast reads and 32 distinct words both cost one LDS pass each — which is exactly the point:
the carry's wall is the FMAs and BF16 rounding behind those reads, not the LDS.

`kernel_price.py work`, per (chunk, head), and per 1024-token wave:

```
modelled intra 2.71 M MAC, inter 3.15 M MAC
executed  intra 2.71 M MAC, inter 76.55 M MAC   = 24.3x the modelled carry
per wave (4,608 chunk-heads): modelled 54.03 GFLOP (reproduces Phase 0's 54.03)
                              executed 730.4 GFLOP = 13.5x
                              duplicated work alone 676.4 GFLOP
```

### The attribution of the added 1,622 ms

Chunked GDN line = 1953.7 − 331.2 + 127.0 ≈ **1,750 ms** against `gdn_rec`'s 127.0 ms (13.8×); added
wall **1,622 ms**. Read the executed arithmetic back as a rate: 730.4 GFLOP / 1.750 s =
**0.417 TF/s**.

| part | price | share of +1,622 ms |
|---|---|---|
| **(a) the serialised carry** — the *useful* inter-chunk work, 29.0 GFLOP, 8 dependent steps per strip-block, 3 `__syncthreads` each | 29.0 GFLOP at 0.417 TF/s = **69 ms**; the exposed serial-chain latency itself is 8 steps × ~500 cyc × ~1 residency round per site ≈ 65 µs per wave | **≈ 4 %**, and the serial *axis* is ≈ 0.004 %. Splitting the chunk axis bought what it said it bought. |
| **(b) LDS occupancy collapse** — `prep` 1 block/CU (12.5 % of the CU's threads), `carry` 2 (25 %) | bounded by `prep`'s entire executed share: 25.0 GFLOP = 94 ms at the worst measured hand-loop rate, ~30 ms at the achieved one. The separate LDS-bank term is real but small: half of `prep`'s 2,454 M lane-reads per wave are 32-way conflicted (`kst[s]` at a `GC_D`-word lane stride) = **~14 ms**, ~0.5 ms with the pitch padded to `GC_D+1` words; the `carry`'s hot reads broadcast, so its whole LDS term is ~2 ms | **≤ 10 %**, and not separable from (d) without counters. Real, cheap to fix, not the wall. |
| **(c) launch count** | 72 launches × 1.8 µs = **0.13 ms**, replacing 18,432 ≈ 33.2 ms of eager-floor dispatch | **a credit, not a cost: −33 ms.** The dispatch half of the cost model worked exactly as priced. |
| **(d) work the kernel repeats** | duplicated carry arithmetic **676.4 GFLOP of the 730.4 executed**. At the achieved 0.417 TF/s: **1,622 ms**. Priced at the two measured hand-loop rates: 796 ms @ 0.85, 2,531 ms @ 0.267 — the measured line sits inside that band; even at the fp32 vector *ceiling* it is 231 ms, larger than (a)+(b)+(c) combined by 8× | **≈ 99 %** |

Secondary traffic, for completeness: staging (`nv` F32 + `kcd`/`qg`/`kh`/`intra` BF16, written by
`prep` and read back by `carry`) is 22,528 B per token per layer each way ≈ 830 MB per wave; state
read+written once per body is 72 MB; `u`/`o` ≈ 590 MB. Total ≈ 1.5 GB per wave = **6.3 ms** at the
237 GB/s DRAM read ceiling. Bytes are not the problem either way — which is the difference between
this line and the sequential one, whose 38.65 GB of per-token state traffic *is* a third of its
127 ms.

**The honest gap.** (a)+(b)+(c)+(d) at the achieved rate reproduces the measurement only because (d)
dominates; if you refuse to price the duplicated work at the achieved rate, the independently
priceable walls (arithmetic at 0.85 TF/s = 859 ms, LDS ~16 ms, issue ~100 ms, traffic 6 ms) total
~900 ms against a measured ~1,750 ms, and the residual is latency exposure at 12.5–25 % occupancy —
the same shape as `progress/2026-10-14/attn-wave-diagnosis-2026-10-14.md` §3's open item, which also could not be
closed on paper. The counters that close it are in §1c.4. Either way the conclusion is the same,
because the duplicated work is *at least* 796 ms of a 1,622 ms wall under the most generous rate in
the measured band.

### Best case for this geometry

Both fixes applied — the `khat` expression (§1c.1) and `jl` wired so the carry stops recomputing the
strip 32× — and nothing else:

| work per wave | at 0.85 TF/s (engine's best hand GEMM) | at 2.93 TF/s (fp32 vector ceiling) |
|---|---|---|
| 54.03 GFLOP, D4 as written | **63.7 ms** — dead on the win line | 18.6 ms |
| 49.20 GFLOP, D4's discarded upper half also gone | **58.0 ms** | 16.9 ms |

Required sustained rate: **0.858 TF/s to hit 63 ms** = 101 % of the engine's best hand GEMM and 29 %
of the vector ceiling; 0.643 TF/s for the 84 ms kill line. Phase 0's own table (§5 of
`progress/2026-10-14/p9-phase1-2026-10-14.md`) said the same thing before any of this was built — "0.862 for 2×,
101 % of the engine's worst existing GEMM" — and that row should have read as a kill rather than a
target. As built, the kernel runs at **0.417 TF/s on the work it actually does**, which is below
Phase 0's break-even of 0.431 TF/s; removing the duplication does not change the instruction mix per
*useful* MAC (one LDS load + one BF16 round + one FMA), so the honest post-fix projection at the
achieved rate is **~117 ms** (range 100–140 ms), i.e. ~1.09× against today's 127 ms, over the 84 ms
kill line.

## 1c.3 Q3 — the decision: **kill P9's chunked scan**

**Recommendation: (ii), kill.** Not a coin flip, and the arithmetic is what makes it so:

1. The chunked form's modelled work is **54.03 GFLOP/wave, +59 % over the sequential form's 33.94**
   (§04.7's UT solve is what the extra costs). To convert that into the pre-registered ≤63 ms it must
   sustain 0.858 TF/s — **101 % of the best hand-written loop this engine has ever produced**, in a
   shape whose every MAC depends on an LDS load, at 12.5–25 % occupancy. Nothing vector-path in this
   repo is above 0.85 TF/s, and this kernel measured 0.417 TF/s on its own executed work, below
   Phase 0's break-even.
2. The two fixes worth having are worth ~1.1×, not ~2×. `jl` wired and `khat` corrected projects
   ~117 ms (100–140) — over the 84 ms kill line. Phase 1b's own verdict asked for a factor of 26 in
   the right direction; the fixes are a factor of 15 of a factor of 26.
3. The remaining sequential line is mostly *overhead*, and overhead does not need a new algorithm.
   `gdn_rec`'s 127 ms = 18,432 launches (≈33 ms of eager-floor dispatch) + 38.65 GB of per-token
   state traffic (≈42 ms at the measured 918 GB/s for a resident set) + 33.94 GFLOP of arithmetic
   (11.6 ms at the vector ceiling, 40 ms at 0.85) + per-token block-reduction latency. Two of those
   three terms are removable **without touching one bit of §04.4's arithmetic**.

**Route A — the one to fund: launch-collapse the sequential recurrence.** Keep §04.4's per-token
recurrence verbatim; change only the *dispatch and residency* shape: one launch per (layer, body),
grid `(d_v/32, heads)` = 64 blocks, each block owning a `[128][32]` F32 state strip **in LDS**
(16 KiB — `gdn_chunk_carry` already proves this fits, twice over) and walking the body's 512 tokens
inside the block. What it removes: 18,432 → 72 launches (−33 ms) and 38.65 GB → ~72 MB of state
traffic (−42 ms). What it keeps: **bit-identical arithmetic**, so no new deviation band, no new
`MAXSC` argument, no re-gating of the decode path, and `prototype/gdn_chunk/`'s CPU contract becomes
unnecessary. Its flops are 33.94 GFLOP/wave = **42 % below** the chunked form's. Projected line:
11.6 ms at the vector ceiling, **40 ms at 0.85 TF/s**, 81 ms at the current 0.417 TF/s → honest band
**40–80 ms**, i.e. it clears 63 ms only if it sustains ≥0.54 TF/s. The serial-depth risk is the
mirror image of P9's: 512 token-steps per block instead of 8 chunk-steps, at ~100–300 cycles per
step (one block reduction + the rank-1 update) ≈ 2.5 ms per wave, which is not the binding term —
arithmetic is. Cheaper to build than Phase 1 already cost, because `rec_kernel`'s body already exists
in `engine/kernels_gdn.cpp` and the residency pattern already exists in `gdn_chunk_carry`.
**The same rate uncertainty is the crux here**, and it should be bought cheaply: the first
commit of Route A is a 512-token single-site probe whose only output is ms, which answers the
0.54 TF/s question for both routes at once and costs one build.
4. **Route B — the bigger, better-evidenced half of the same wave: attention.** `attn` is 109.2 ms
   (33 % of the post-flip wave), i.e. the same size as `gdn_rec`, and unlike GDN its mechanism is
   *measured* (the counter pass in `progress/2026-10-14/attn-wave-diagnosis-2026-10-14.md` §1–2, §9) with a tiling
   spec and a projected **8.8–30 ms**. Per unit of evidence, that is the better-funded package.
5. **Route C — the only arm that raises the ceiling: matrix units.** The ISA census above shows
   `v_mfma = 0`: this engine has no matrix-unit instruction anywhere, so every hand kernel fights the
   2.93 TF/s vector ceiling while hipBLAS's bf16 path measures 4.7–5.9 TF/s on this box. The whole
   chunked plan at 2 TF/s is 27 ms. If prefill *arithmetic* is the thing to attack — the UT solve, the
   `[C,C]` matrices, the carry — then MFMA/rocwmma is a decision with a measured ceiling behind it,
   and it is a decision (the operands have to be staged for `v_mfma_f32_bf16_bf16_f32` tiles), not a
   kernel tweak. This is the honest answer to "how would the chunked form ever reach 0.86 TF/s": it
   would need matrix units, at which point the UT-transform flops stop being a liability and the
   `+59 %` argument inverts.

**What must be done regardless of which route is funded:**

* **Apply the §1c.1 one-liner or make the path refuse.** `--gdn-scan chunk` is reachable in the tree
  and returns NaN for any body whose within-chunk gate sum passes −87, which is most real prompts.
  Today `--gdn-scan` defaults to `seq`, so the shipping path is unaffected; but the next person who
  runs `chunk` on a 300-token prompt will get token 0 and a confusing gate. The one-line fix is in
  §1c.1; the alternative is to have `engine/decode_step.cpp` reject `chunk` with the reason printed,
  which is a gate-policy call and therefore the parent's.
* **D6 is recorded** in `gdn_chunk_kernels.h`'s deviation block, comment-only, naming the line, the
  model's expression, the underflow threshold, and the reproducer. `jl`'s dead-variable note is at its
  own line. No code changed by this pass, so no bit moved and no gate can change colour.
* **`AGENTS.md`'s traps table** should gain the general form of this bug, which is not GDN-specific:
  *an algebraically-equal rewrite that divides two underflowing `exp`s is NaN where the original was
  0 or 1; a rewrite of a decay ratio must keep the subtraction inside the `exp`.* It presented as a
  carry-geometry bug, reproduced only at ≥2 chunks, and the one-chunk fixture that "passed" was
  poisoned too (p64: 114,688 NaN state elements with no output row to show it).

## 1c.4 Hand-off: the device commands, and what this pass does not claim

Nothing below was run by this pass. Ordering per `AGENTS.md`: blocking, one at a time, GPU lock by
TAG, and `prototype/gdn_chunk` is not one of the self-locking drivers — check with
`grep -c gpu_lock prototype/gdn_chunk/*.py` before holding the lock around it.

1. **Confirm D6 on device, cheapest form first.** Apply the one-line `khat` fix, then
   `engine/gate.py --gdn-scan chunk` on `p64` and `p300` (the two fixtures where the mirror predicts
   a difference: p64 should go from 114,688 NaN state elements to 0, p300 from first-NaN row 64 to
   none) and `wide1024f`, where the prediction is that the first answer token stops being `0`. If
   `wide1024f` still disagrees with its pin after the fix, there is a **second** defect and Phase 1c's
   Q1 is necessary-but-not-sufficient — say so loudly, because §1c.1's claim is then incomplete.
2. **Counters, if the parent wants the residual closed** (the ~900 ms of latency exposure in §1c.2) —
   the same four that closed attention's §3: `SQ_INSTS_VALU`, `SQ_INSTS_VALU_FP64`… use
   `SQ_INSTS_VALU`, `SQ_INSTS_LDS`, `SQ_WAVES`, and `FETCH_*`/`WRITE_*` DRAM bytes, per kernel, on a
   1024-row wave with `--gdn-scan chunk`. `SQ_WAVES ≈ 4,608 + 2,304` would confirm the grid arithmetic
   in §1c.2; `SQ_INSTS_VALU / SQ_INSTS_LDS ≈ 3–4` would confirm the 32× duplication independently of
   reading the source.
3. **If Route A is funded, the first device run is the single-site probe** (one layer-body,
   512 tokens, resident strip, `ms` only) whose whole job is the ≥0.54 TF/s question. It must be
   main-agent-run: it is a timing, and it decides a funding line.
4. CPU-side, no device needed: `argmax(all-NaN F32 row)` with a strict-`>` loop returns index 0. That
   is §1c.1's last inference and it is a three-line check.

Not claimed by this pass:

* No device measurement of any kind. Every millisecond in §1c.2 is arithmetic on `devices/` rates,
  Phase 1b's two device-window numbers, and the compiler's own resource report.
* The post-fix projection (~117 ms, range 100–140) is an extrapolation of the achieved rate onto
  de-duplicated work, not a measurement. It is the number the kill decision rests on, together with
  the 0.858 TF/s requirement.
* The mirror does not model LDS sizing, block geometry, the thread mapping, or D1. `candidates` shows
  residency is arithmetically a no-op, which is why the LDS/Occupancy story could not have produced
  the NaN — but it also means the mirror cannot be used to predict a *performance* change, and it is
  not a witness for §1c.2's arithmetic (that is `kernel_price.py`, which is geometry and flop
  accounting, not a value model).
* Whether a third defect sits behind D6 on `wide1024f` is unknown until item 1 runs.
