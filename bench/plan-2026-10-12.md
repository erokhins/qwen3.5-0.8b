# Plan after the first engine gate pass (set 2026-10-11 evening, user-directed order)

Context: `engine/gate.py` PASSes end to end on `dec8` — 93 checks, all 8 pinned greedy ids
exact, logits `cos` 0.999886–0.999968, **~83 tok/s** (11.978/12.053/12.232 ms/step, spread
2.1 %, clean window). Gate policy decided: **G5's `cos >= 0.9995` stays the hard floor** for
end-to-end token logits, G6's 0.9999 stays advisory — an end-to-end quantity has accumulated
error across 24 layers and must not be held to a per-stage bound.

Rules that bind every item: `AGENTS.md` (one subagent at a time; workers may run short
correctness-only device checks < 60 s but **never** a timing; the main agent owns every number
that enters `bench/performance-status.md`; commit by topic with explicit pathspecs; **never
write chat-template special tokens literally — refer to them by id**).

## P1 — deepen correctness before anything else (next worker)

> **Standing rule for every deep or long-context fixture (user-directed, 2026-10-12): the prompt must
> actually generate a lot of tokens.** A fixture whose continuation reaches the stop id after a handful
> of tokens cannot test depth at all, and worse it makes the chain cross its own end-of-turn, which
> confounds the state-carry-over signal — that is exactly what happened to `dec64f`, which emits 248046
> at step 24 so that steps 25–34 are simultaneously post-stop and low-signal. Enforce it mechanically:
> **pre-flight with `tools/stop_probe.py`, require no stop id for the whole intended generation
> (target ≥128 free tokens; ≥80 before pinning anything), and record the first-stop index in the fixture
> manifest.** Probed and known to run ≥120 tokens with no stop: the count-from-1-to-80 chain (`dec64t`,
> none in 300), a 200-word Paris paragraph, the months-and-lengths list, a bicycle explanation, a
> prime-number continuation. For long-context work drive **both** axes — a long prompt *and* a long
> generation — because context length, not step count, is what moves the attention lane count.

1. **Pin a 64-step FORCED-decoding fixture (`dec64f`) — not a free-run pin.** Free-running
   cannot be pinned 64 deep, and this is a measured limit, not caution: **A-18**
   (`specification/ASSUMPTIONS.md`) records that greedy bf16 continuations are chaotic beyond
   ~4–8 tokens, with HF-sdpa vs HF-eager — the reference against a legal rounding variant of
   itself — agreeing only **0.8776** of the way over 49 prompts × 24 tokens. A correct engine
   asked for 64 free-run ids would therefore *fail by construction*; §10 stops token parity at
   the first flip for exactly this reason. So: feed the reference's **own** token at each step
   for 64 steps and compare logits + sampled id per step (teacher forcing). No divergence
   cascade can enter, so depth is free, and what it actually tests is state carry-over — GDN
   state, conv window, KV — 64 steps deep instead of 8. New fixture via
   `tools/reference_dump.py` (CPU, no GPU) under `data/refs/`, with the byte-for-byte
   reproduction check per §10.5.
   - **Disk budget: ~64 MB, not ~1.7 GB.** `data/refs/dec8` is **292 MB for 8 steps** =
     25.9 MB/step, because each step pins ~500 per-layer operand files (~1 MB of logits,
     `logits_last.npy` is 993,408 B). Pin per step: logits + sampled id + state deltas only;
     keep full per-layer operands at 1–2 steps. A naive 64-step pin is a 1.7 GB fixture.
   - Free-run parity stays bounded by A-18: keep the ≤8-token exact-id check (`dec8` already
     covers it) and treat the 300-token run in item 2 as smoke, never as a parity claim.
2. **Run the engine 300 tokens as a smoke test** on top of that: no crash, no NaN, state within
   bounds, ends by length or by the stop id. Parity is claimed only over the pinned 64.
3. **`MAXSC = 512` must be dealt with, not discovered later.** `engine/kernels_attn.cpp` throws
   above 512 lanes. 17 + 64 = 81 lanes is fine, but a 300-token prompt fixture plus a 300-token
   generation is ~600 lanes. Either raise the cap with a measured justification or implement the
   split-block form §07.3 describes; decide by measurement, and say which was chosen.
4. Report per-step `cos`/`meanrel` for all 64 steps so a drift-after-token-8 class bug (the
   conv-window rollback risk named in the hand-off) cannot hide.

## P1b — `dec64t`: a deep fixture with no end-of-turn crossing (user-directed)

`dec64f`'s forced chain emits the stop id (248046) at step 24, so steps 27–34 are **both** the
low-signal window (pinned `S n2` halves, `corr(1−cos, 1/S n2) = 0.769`) and the post-stop window —
the two explanations are not separable on that fixture. Fix: a prompt engineered to run well past
64 tokens ("Count from 1 to 80, separating the numbers with commas.", or a ≥200-word paragraph
request), through the same chat template, **pre-checked to hold ≥80 tokens before the stop id**.
Same lean pin policy as `dec64f` (~60 MB), `--verify` byte-for-byte. Then re-run engine-vs-pin and
route-vs-route per step: dips that track energy and stay put here confirm the scale explanation;
dips that follow the crossing mean `dec64f`'s 27–34 should be labelled a stop-crossing artifact.
Side benefit: a clean prompt gives an honest **free-run id agreement depth** (A-18 predicts ~4–8;
measure wherever it lands — closest thing to a deep free-run G7).

## P1c — engine G7 at breadth (queued behind the band option-1 work)

The engine is proven on three fixtures, all single-turn and ≤327 lanes. Add breadth, with the prompt rule
above applying to every one of them:

1. **Long-context forced-depth fixture** — a long prompt (target ~300 tokens) *plus* ≥128 forced steps,
   so lanes go past 400 and approach the `MAXSC = 512` cap. This is the fixture that turns the split-block
   attention work from a hypothetical into a requirement, and it exercises §07.3's online softmax at a
   lane count `dec8` never reached.
2. **Multi-turn chat fixture** — a transcript with an assistant turn long enough to matter, because
   `engine/chat.sh` is now the user-facing surface and nothing tests a second turn's state (cache carry
   across turns, the `feed`/`gen` session invariants the chat driver found by running it).
3. **Free-run agreement depth measured, not assumed** — `dec64t` gave 64/64 identical free-run ids on a
   deterministic counting prompt; re-measure on a *prose* prompt and report where divergence starts, since
   A-18 predicts ~4–8 tokens and the counting chain was plainly a lucky case. Wherever it lands, that is
   the closest thing to a deep free-run G7 we can honestly claim.

## P2 — `engine/chat.sh` (analogous to `speccheck/chat.sh`)

Mirror `speccheck/chat.sh`: REPL + `--prompt` one-shot + `--max-new`, per-turn stats
(prompt tokens, generated tokens, tok/s, time-to-first-token), same flag surface where the
meaning carries (`--max-new`, `--model`). Differences to state in the header: this drives the
**HIP engine** via `engine/build/decode_run`, it is GPU-resident, and its numbers are not
ledger numbers unless taken under the §6 rules. The speccheck original notes torch CPU, bf16,
greedy, `OMP_NUM_THREADS=8` to stop torch oversubscribing — the engine version needs the
opposite note (one device, no thread knob).

## P3 — detailed performance: prefill and generation, then store it

**Prefill is not implemented** — the prompt is currently fed one token per decode step (17 of
the 81 steps in the timing runs were prompt steps), so there is no time-to-first-token figure
to measure yet. Order inside this item:

1. **W7 prefill (§06)** — chunked/parallel prefill pass plus its gate against the pinned prefill
   dumps. Until this exists, "prefill performance" means the token-at-a-time surrogate and must
   be labelled as such.
2. **Measure, blocking, zero subagents, best-of-N with spread stated:**
   - prefill ms vs context length (64 / 256 / 1024 / 3072) → time-to-first-token curve;
   - decode ms/token vs context length — attention traffic scales with context, so short-context
     tok/s is an optimistic bound and the ledger must say so;
   - the gap items from the attribution: 424 launches/token, 115 of them dtype casts
     (~0.4 ms of dispatch), per-step sync in the argmax path, HIP graphs (~4 % known ceiling).
3. Store in `bench/performance-status.md` §6 with provenance (lock tag, `util` discounted,
   spread), and correct §3's stale projection figures if the real numbers contradict them.
