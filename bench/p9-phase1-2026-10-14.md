## 3. Two proofs the recurrence change is structurally safe

**The wave-body hand-off is bit-identical, not approximately so.** The engine prefills in `wave_rows`
bodies and resumes requests mid-sequence, so a chunked kernel is handed a state and must hand one
back. `split` cuts each fixture's pinned operands at a multiple of C and requires
`cat(o[0:c], o_with_S_from_first_segment[c:]) == o_all` and `S_2 == S_all` **bit for bit** — 20/20
PASS over C ∈ {16,32,64} on p64 and p300. Its control is the aligned cut plus one token, which **must**
differ and does at every C; without that control the PASS would be a tautology. Two honest limits: no
stage-pinned fixture is long enough to contain the engine's real 512-row body boundary (p300 at 277
tokens is the longest, and the wide fixtures pin logits but no GDN operands), so the 512 boundary
itself is covered by *C* dividing 512 plus the arbitrary-cut carry check rather than by a direct
measurement at 512; and that carry check is Phase 0's, which cut the same operands at 92/100/177 —
non-multiples of every C — and got 45/45 PASS against the pins with a zero-initialised second segment
scoring state meanrel 6e-1 as its non-vacuity control. Consequence of the two together: with
C ∈ {16,32,64} dividing 512, the engine's body schedule is not part of the numerics, and a per-body
gate result reads as a whole-prompt claim.

**A one-row body has no scan to chunk — measured, not asserted.** `onerow` runs a T=1 body through
both forms on the pinned operands (p300 row 0, and `wide1024f`'s `decode7` pins, which are
one-row bodies from a real 1024-token request). The **state** comes out bit-identical: at T=1 the UT
system is a 1×1 unit matrix, so the solve is the identity and the write degenerates to §04.4's. The
**read does not**: the chunked form computes `Γ(q·S) + (q·k)·dv`, which is exactly the split read
§04.4 warns about, worth ~2e-7 `meanrel` per layer against the sequential form. So decode
bit-identity under `--gdn-scan chunk` is a property of the **dispatch rule** (a one-row body must
still run `rec_kernel`), not of the algebra — the rule is load-bearing, and the device decode A/B is
the only thing that can show byte-identical output. Anyone who writes the kernel should treat
`tokens == 1 → rec_kernel` as a refusal list, not a fast path.

## 4. Three negatives that localise

Injected in `chunk_scan.py` beside Phase 0's seven; the must-catch/must-not-catch sets below are
**derived** from (T, C, H) and the corrupted operand, not hand-listed (the `AGENTS.md` trap: a
hand-listed set rots into "everything" the moment the fixture changes). Measured on p300 L00, T=277,
C=64, 5 chunks; the threshold is 100× the legal route delta, which is itself measured (max|Δo| legal
= 2.384e-7 → threshold 2.384e-5).

| injected bug | what it corrupts | derived unreachable set | measured per-chunk max&#124;Δo&#124; (c0…c4) | verdict |
|---|---|---|---|---|
| `carry_stale_state` | the inter-chunk carry (chunk *i* reads the state as of *i−2*) | chunk 0, every row | `0.0 1.9e-1 3.8e-2 1.2e-1 1.1e-1` | PASS |
| `decay_off_by_one` | the intra-chunk decay product `M_ij` (uses `γ_{i−1}`) | chunk 0 row 0 only | `2.5e+0 2.2e+0 1.3e+0 2.5e+0 2.5e+0` | PASS |
| `boundary_wrong_head` | the chunk-boundary decay of `S_in` (head *h* gets head *h−1*'s) | chunks 0 **and** 1 | `0.0 0.0 1.4e-1 9.9e-2 1.2e-1` | PASS |

Why each unreachable set is what it is, in one line each: a stale carry has nothing to be stale about
in chunk 0, whose read *is* the request's incoming state; row 0 of chunk 0 has exactly one
sub-diagonal entry, `exp(γ₀−γ₀)=1`, which the off-by-one shift leaves bit-identical; and a wrong-head
boundary multiplies `S_in` **only**, so it is invisible in chunk 0 (where `S_in = 0`) *and* in chunk 1
(which reads the state chunk 0 wrote, untouched by the decay) — first damage at chunk 2.

All three are **exact zeros** on their unreachable cells (not small numbers — the arithmetic path is
untouched there), loud above the threshold on every reachable chunk, and each trips the `meanrel`
ceiling against the pins (o meanrel 1.60e-1 / 8.72e-1 / 1.25e-1; state 5.07e-1 / 2.76e-2 / 7.00e-1).
The wrong-head bug is additionally required to differ from its **head-blind sibling** (`no_chunk_decay`,
same operand, no head axis): `|per-head profile − sibling's profile| = 1.4e-1 ≫ threshold`, otherwise
"every head moved" would be a claim the instrument could not have falsified. Calibration follows
Phase 0 §1.4: the legal chunk-vs-sequential delta is the floor every bug must clear by 100×.

## 6. The kernel spec, and the one constraint that stopped this pass

Written so the kernel can be built from it, and deliberately not started.

**The two phases, and why they are two.** Per (layer, body) the chunked scan splits into head-local
prep (normalise q/k, the cumulated log-decay, the UT system and its application to two right-hand
sides, the intra-chunk attention) — embarrassingly parallel over (head, chunk), 16 × 8 = 128 blocks —
and the serial carry (`v_new = nv − kcd·S`, `o = q̃·S + intra·dv`, `S = cdec·S + k̂ᵀdv`), parallel over
(head, d_v-strip): every quantity in the carry is column-local in `d_v`, so a 32-column strip is a
self-contained block and the state strip is 128×32×4 = 16 KiB of LDS. That is 16 × 4 = 64 blocks per
(layer, body), 8 serial steps each — enough blocks to keep 20 CUs fed, which is exactly what today's
`<<<NH, D>>>` one-launch-per-token shape is not.

**The constraint that makes C=16 the easy size and C=32/64 the designed one.** The prep phase needs
the chunk's normalised `k̃` (and `q̃`) resident: the UT system and the intra attention are all-pairs
128-dots, so `k̃` cannot be recomputed per pair. At C=64 that is 64×128×4 = 32 KiB for `k̃`, another
32 KiB for `q̃`, and 16 KiB for the `[C,C]` UT matrix while the forward substitution runs — **≥ 80 KiB
against the engine's recorded working ceiling of ~38.9 KB per block** (the value
`prototype/attn_decode` §12 measures `attn_core` against). So a C=32/64 prep block must either stage
`k̃`/`q̃` as BF16 (which halves them and is also what the matrix-unit operands would see, so it costs
nothing in honesty — but then the CPU model must round the same operands, and it already does) or
build the two `[C,C]` matrices in row-strips of 16 rows, which keeps the block near 24 KiB at the
cost of one more loop. Neither is hard; both are a design decision, and Phase 0's cost model priced
flops, not LDS.

**Layout facts the kernel must not re-derive.** `S` is `[h][d_k][d_v]` F32 in global memory
(`rec_kernel`'s `Sh[i*D + j]`), the `u` tile is `[rows][6144]` with q at +0, k at +2048, v at +4096 and
each slice head-major `[16][128]`, and `q̃`/`k̃` are normalised **inside** the kernel
(`kq * rsqrtf(block_sum(kq*kq)+1e-6f)`, `Q_SCALE` on q only) — reusing that expression verbatim is
what keeps the prefill-side operands bit-comparable with what the decode path already feeds the pins.
The ragged tail pads with `β = 0, g = 0` (§04.7, A-08), and `chunk_scan.py`'s own selftest already
asserts that padding moves no real row and no final state.

**Flag plan (lands with the kernel, in one commit).** `--gdn-scan seq|chunk` and `--gdn-chunk 16|32|64`
on `DecodeScratch` exactly as `--attn-tile` rides it (`decode_run.cpp` parses-or-throws, echoes
`gdn_scan=`/`gdn_chunk=` on the `NUMERICS` provenance line, `submit_wave_body` reads `sc`), default
`seq`; **`tokens == 1` dispatches to `rec_kernel` regardless** (§3); refuse rather than fall back if
the chunk plan is unsuitable, because a silent fallback prices one form and reports the other. Two
consequences the parent owns, both of which are `engine/gate.py` and therefore outside this pass:
section (h) re-derives the launch plan from §07 and will disagree with a 72-launch GDN family until
it is told about it, and `stage_clock`'s `gdn_rec` family needs a name for the chunked path or the
before/after attribution will fold two different shapes into one row.

default to C=64 and either reject smaller chunk sizes with this number attached, or widen nothing and keep the gate
as the arbiter. Phase 0's cost table favoured small C for speed; the budget vetoes it, and the veto wins.

| the launch plan | `engine/stage_clock.{h,cpp}` | new `kGdnChunk` family (one site per layer per body), `WaveShape::gdn_chunked`, and a plan bill that *derives* the seq/chunk split from `tokens`/`bodies`/`wave_rows` — so a `--gdn-scan chunk` run whose final body is one row still bills that body's token to `gdn_rec`, which is what makes the plan row and the counted row able to agree. |
| the gate side | `engine/gate.py` | `--gdn-scan` / `--gdn-chunk` forwarded to every run (including the wave-width A/B sides) and asserted against the `NUMERICS` echo, same instrument as `--attn-tile`. |

**The one-row rule lives in one function.** `resolve_gdn_scan(want, rows)` returns `kSeq` when
`rows == 1`, and `gdn_chunk_prefill` throws if it is ever reached with `n < 2`. The witness for why
that is load-bearing and not cosmetic is `prototype/gdn_chunk/phase1.py onerow`, re-run in this pass:
on a one-row body the chunked form's **state is bit-identical** to §04.4 but its **`o` is not**
(worst meanrel `2.66e-07`, cos `1.00000000`, at every layer probed, from a zero state and a carried
one). Same numbers, different last bits, because the chunked form reads the state it just wrote as a
BF16 matmul operand where §04.4 reads the F32 value. That is under every band we have and it is still
not spent: decode's claim is byte-identity. `split` re-run too — aligned body splits bit-identical,
the non-aligned control not.

## 1b.1 Deviations from the Phase 0 contract, and which ones can change bits

Stated here **before** any device number, because two of them can move bits and the gate must not be
tuned around them after the fact. Full text at the top of the kernel header.

* **D1, changes bits.** F32 accumulation order in every dot: a thread walks its reduction serially,
  the CPU model asks torch for a bf16 matmul. This is §10.1's class — a chained dot's legal ndiff is
  29–47 % — and it is the reason the chunked form is *band*-gated and no check here may demand
  bit-identity with the mirror.
* **D2, changes bits, ≤ 1 operand-ULP.** `k~` is staged in LDS as BF16. Exactly what the model rounds
  `k~` to where `k~` is itself an operand, so free there; but `k·beta` (`ut`'s first operand),
  `k·beta·Gamma` (`kcd`'s right-hand side) and `khat` are then derived from a BF16 `k~` and rounded
  twice where the model rounds once. The line it buys is LDS: F32 `k~` (32 KiB) + the F32 `C×C` matrix
  (16 KiB) is 48 KiB, over the ~38.9 KiB per-block ceiling `attn_decode` §12 recorded; BF16 `k~` puts
  the block at ~33 KiB. **The §6 row-strip alternative (build the `[C,C]` matrices in strips of 16
  rows, ~24 KiB) is the first move if these three operands are what a profile blames.**
* **D3–D5, no bit change.** staging through LDS/global scratch instead of registers; evaluating the
  upper half of the `[C,C]` products and throwing it away (this is `dec.tril()`, and it is wasted
  flops, not wrong bits); a single-thread 64-add prefix sum for the intra-chunk cumsum.

Not a deviation but worth naming: `U` is held F32 and rounded to BF16 **at use**, and `nv` stays F32,
because that is what `chunk_scan.py` does and says it does.

## 1b.2 What the shape costs, and the line it has to clear

Launches per GDN layer per body: **1 → 2** (`prep`, `carry`); per 1024-token wave at 512-row bodies:
**18,432 → 72** sites-and-launches from `gdn_rec`'s 18,432, i.e. the ~33.2 ms of dispatch §5 priced
buys down to ~0.2 ms. State traffic: the carry reads and writes the `[16][128][128]` block **once per
body** instead of once per token, so §5's 38.65 GB of per-wave state traffic becomes ~0.6 GB. What
that does *not* buy is flops — Phase 0 §5 priced C=64 at **118.8 GFLOP/wave vs the sequential form's
74.6**, +59 %, and the vector-path ceiling is 2.93 TF/s, i.e. 40.6 ms of unavoidable arithmetic.

**The win line is §7's, unchanged and pre-registered: `gdn_rec` ≤ 63 ms of the 125.4 ms line, or the
form does not ship.** Re-read against this implementation, clearing it needs **~0.86 TF/s sustained**
(1.99×). This kernel is hand FMA loops with BF16 operands and no MFMA, so that is ~101 % of the
engine's own hand-GEMM rate (0.85 TF/s) and 29 % of the vector ceiling: the honest prior is that a
first version lands in the 63–84 ms band or worse, and §7's middle rule applies there (the wave total
must also drop, and the judgement is explicitly about launch-count headroom bought for arithmetic).
> 84 ms → killed. No number is claimed here; none was taken.

## 1b.3 Negative controls, and what is missing from them

Four injections are in the kernel (`GdnChunkNeg`), each with its must-move and must-not-move sets
**derived from the geometry** rather than hand-listed:

| injection | must move | cannot move |
|---|---|---|
| `GCK_CARRY_STALE` the inter-chunk carry re-reads the pre-body state | every row of chunks ≥ 1 | chunk 0's rows and state; any one-chunk body |
| `GCK_BOUND_HEAD` the boundary update reads head `(h+1)%16` | every row of chunks ≥ 1, per head | chunk 0's rows; any one-chunk body |
| `GCK_UT_NO_DECAY` `dec[t,s] = 1` | every row except a chunk's row 0 | a chunk's row 0 (its only `s` is `t`, where `dec = exp(0) = 1`) |
| `GCK_PAD_ROW` the ragged tail is not padded | the tail body's final state | every body whose `n` is a multiple of 64; no output row moves |

**Gap, stated rather than left implicit:** the engine always passes `GCK_NONE` (the engine is not a
place to inject bugs, `kernels.h:16`), and Phase 1b had no budget for the op's device host, so there
is **no driver for these four yet**. `prototype/gdn_chunk/` has a CPU judge and no `.hip` host, so the
injections are compiled and unreachable. Whoever runs the device pass should know the negative half of
the matrix is not runnable until that host exists — it is ~80 lines of the shape
`prototype/gdn_decode/gdn_decode.hip.cpp` already is, pointed at these two kernels.

## 1b.6 Two defects found by review before the device ever saw it

Recorded because both are this repo's documented failure shape, and because a device run would have
presented them as something else entirely.

1. **`U`'s row 0 was never initialised.** The substitution writes row `t` of `U` over row `t` of `ut`,
   in ascending order, and row 0 of `ut` is empty — the strict lower of row 0 has no entries — so the
   pair loop wrote nothing there and the loop started at `t = 1`. Row 1's `U` is `-ut[1][0] * U[0]`,
   i.e. every row of every subsequent sum reads row 0 of LDS shared memory that nothing had ever
   written. Not a wrong bit: the whole solve, from a buffer that reads as whatever the previous block
   left. Fixed by seeding `m[0][tid] = (tid == 0)` before the loop, which is `ut_inverse`'s `i = 0`
   case (`e_0`, nothing subtracted) spelled in the place the kernel needs it.
2. **The tail chunk's staging was read where it had not been written.** A tail chunk of `GC_C` rows may
   be mostly padding — `--wave-rows 5` makes every body's tail chunk one — and the first version wrote
   `nv`/`kcd`/`qg`/`kh`/`intra` only for rows the body actually had, while the carry looped all `GC_C`
   rows of the chunk and read all of them. Uninitialized scratch feeding the state update, and past the
   end of a small scratch on the way. Fixed on both sides: prep writes staging only for rows that exist
   (writing the padding rows would index past a body of `n < wave_rows` rows), and every carry loop now
   bounds its reads by the chunk's valid rows, which is also what makes `GCK_PAD_ROW`'s observable
   effect exactly what its comment claims — the wrong `cdec`, hence the final state, and no output row.

One correction to §1b.4's matrix, because `--scope` (§18.2) has the same job here it had for the tiled
attention core and it is not the job of naming the form. The wave-width checks in section (h) hold the
GDN scan identical on both sides — `run_batched_ab` forwards `--gdn-scan` to every side, so "both sides
ran the same scan" was already true and cannot adjudicate a carry failure. So:

* run the matrix above at `--scope full` on **both** forms. `seq` is the shipping default and its
  verdict must be the whole verdict, carry checks included; the chunk side runs full too, and if it is
  green there is nothing to attribute.
* if the chunk side fails, re-run it `--gdn-scan chunk --scope form` and diff
  `wave_carry_deferred.json` against the `seq` run's file. A check that fails identically on both scans
  is a wave-carry defect, not a P9 result, and it stays a separate finding either way.

`--scope form` is the right shape for this A/B and is not automatically it. §18.2 deferred the wave-width
output comparisons because they hold the *attention* form identical on both sides, so they cannot say
which form is wrong; the identical argument applies to a wave-width check under a GDN-scan A/B, since
`run_batched_ab` now forwards `--gdn-scan` to every side too. What the flag does not do is decide which
form a *prefill-row* failure belongs to — those are per-run, not per-A/B, and they stay counted on both
sides of this matrix. Whether the deferral should default on for a scan A/B is a gate-policy call
(`SCOPE` is spelled for the attention form today), so the matrix above is written at the default
`--scope full` and the attribution option is named rather than assumed.

## Phase 1b device window (2026-10-14, locks `P9DEV`/`P9DEV2`): **the chunked kernel misses the win line by ~26× and is wrong above one chunk — it does not ship**

| 1024-token wave | `--gdn-scan seq` | `--gdn-scan chunk` |
|---|---|---|
| wave wall | **331.2 ms** | **1953.7 / 2003.5 ms** (two runs) |
| `gdn_rec` | 127.0 ms (38.35 %) | not in the family table at `seq`'s magnitude — the gdn group reads `gdn_all_pct=0.38`, i.e. the time moved somewhere the attribution didn't price |
| win line | — | **≤ 63 ms pre-registered. Missed by roughly a factor of 26 in the wrong direction.** |

**And it is not merely slow — it is wrong where it matters.** `dec8` **PASSES** with `chunk`, but `wide1024f`
**FAILS**: the first answer token comes out `0` where the pin says `279`, and step 0 is a hard miss that neither
the tie policy nor the slack rule admits. That split is diagnostic rather than confusing: **`dec8`'s prompt is 17
tokens, which at C=64 is a single chunk, so the inter-chunk carry — the entire point of the chunked form — is never
executed by any small fixture.** `wide1024f` runs 16 chunks, and the failure appears exactly there. The prime
suspect is the carry (`gdn_chunk_carry`, serial over the chunk axis with the state strip resident in LDS), and the
worker's own §1b review had already flagged the `U` row-0/boundary seeding enough to patch it in `59c43dc` — which
suggests the boundary conditions are the fragile part, not the algebra.

**Consequences, in order.** (1) `--gdn-scan` stays `seq` — no decision needed, the pre-registered line made it
automatically. (2) The CPU contract is still sound: `phase1.py` says the *form* fits Phase 0's budget at C=64 with
zero argmax moves at room ≥ 0.10, and it was the CPU gate that would have caught a numerics problem — what the
device window exposes is an **implementation** defect plus a **cost-model** failure. (3) The cost model now needs
to answer a question it didn't: Phase 0 priced arithmetic and concluded ≥1.5× was available, but the shipped kernel
got ~6× slower, so either the carry launch is pathologically serial (grid `4 × heads` with a 16-step chunk axis
each block walks alone) or the LDS-resident state is throttling occupancy to nothing. **Until that is understood,
P9's funding premise is unproven on device, not merely unquantified.**

**One-line status for the ledger:** chunked GDN scan = CPU contract valid, kernel wrong above one chunk, ~6× slower
than sequential, does not ship; `gdn_rec` remains **127.0 ms / 38.35 %** of prefill and remains the largest single
line in the wave.
