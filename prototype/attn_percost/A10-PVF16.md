# A10-PVF16 — the F16 P·V accumulator, built behind an inert knob, and what the machine said back

Bet: `A10-F16-IMPL.md` D1–D7. Knob: `--attn-fattn-pvf16 {0,1}`, **default 0**, in the shipping attention path
behind `--attn-fattn 1 --attn-tile 1 --attn-touch 1`. State as of 2026-10-20: the code is in the tree, the
compile-side and CPU-side witnesses are done, and **the device gates have not been run** — every device command
this change needs is listed in §6 for the main agent to run in one exclusive window. No timing figure in this
file is a measurement; none of it was taken by a worker (AGENTS, "GPU execution is serialized").

Nothing here widens a band, moves a fixture, or changes a default. `A10-F16-IMPL.md` is unchanged; this file is
the append it asked for.

## 1. What was built

Eight `__global__` spellings instead of four: the third axis (`kPvF16`) is a template parameter, not a runtime
branch, for the standing reason — a branch would move the DEFAULT side's register budget, and "the default is
inert" is only a fact if it is a machine-code compare. One accumulator type per knob side
(`FattnAcc<kPvF16>` = `FattnO` or `FattnO16`), so a default build never has both live.

Sites, as D3 enumerated them:

| site | what moved | what did not |
|---|---|---|
| the accumulator struct | `FattnO16 { fattn_HRegs t[FATTN_VT16]; }` — 8 tiles × 16 halves = 64 VGPR/lane | `FattnO`, unchanged, still 16 × 8 F32 = 128 |
| the P·V leg | two `__builtin_amdgcn_wmma_f16_16x16x16_f16_w32` per 32 dims, `op_sel` 0 then 1, two A fragments (the pair's low and high 16 dims), the same P, the same D block | the A fragments are the same two LDS tiles the F32 leg reads for tiles `2τ` and `2τ+1`; the V stage, its address expression and its two barriers are untouched |
| the rescale fold | the same `expf(m - mn)` on 128 halves in 64 registers, rounded to F16 once per round | its **position** — still on the accumulator's critical path, before the round's add, as D6/§6 require |
| the epilogue drain | `fattn_stage_half<true>` writes dim `fattn_h_dim(lane, τ, e)` and widens each half with `v_cvt_f32_f16` | the publish side of `fattn_transpose_out`, shared by both forms on purpose (§20.1: one address expression for a staged object) |

Plumbing, mirroring `--attn-fattn-qstage` and moved as one set: `engine/kernels.h` (`AttnLayerArgs::fattn_pvf16`),
`engine/decode_step.h` + `.cpp` (the field that rides to the one launcher call site), `engine/decode_run.cpp`
(parse-or-throw, the `--attn-fattn 0` refusal keyed on `..._given` and not on the value, `--help`, the NUMERICS
field `attn_fattn_pvf16=f32|f16`), `engine/kernels_attn.cpp` (the eight-way dispatch, each branch naming its
kernel once and recording the pointer it launched), and `engine/gate.py` (`--attn-fattn-pvf16`, `default="0"`,
forwarded at all three argv sites and asserted against the run's own NUMERICS echo). **The gate default and the
engine default are one commit**; the echo check is what catches a split.

New behavioural canary: `ATTN_FATTN` now prints `pv=f32|f16` beside `q=`/`roll=`, and `vgpr=`/`lds=`/`scratch=`
are still read off the kernel this launch submitted, so the two sides cannot print the same banner.

## 2. The D-block map was measured, not transcribed

`prototype/attn_percost/a10_pvf16_map_probe.cpp` (built by `build_a10_pvf16_map.sh`, which refuses unless the
listing carries ≥ 2 `v_wmma_f16_16x16x16_f16` sites — it emits 4) runs one warp on patterned operands and prints
what each lane holds. `prototype/attn_percost/check_a10_pvf16_map.py` is the permanent witness, and its F16
decoder carries a selftest for the reason `bf16_ulp.py` does: a mis-decoding checker reports a wrong MAP rather
than a broken checker, and mine did exactly that on its first version (`(1 << m)` where `(1 + m/1024)` was
meant — it "failed" a correct map).

The map, 0 disagreements over 32 lanes × 16 elements in **both** `op_sel` orders:

    lane t, element e of tile τ holds query row (t % 16) at dim
        32·τ + 16·(e & 1) + 2·(e >> 1) + (t >> 4)      ==  32·τ + 16·(e & 1) + fattn_c_col(t, e >> 1)

i.e. the shipped F32 C-tile law applied to each `op_sel` half with `l = e >> 1`, plus the half-of-pair offset.
Element `2l` is the LOW half of VGPR `l` and carries dims `0..15` of the pair; element `2l+1` is the HIGH half
and carries `16..31`. Exchanging which A fragment gets `op_sel` 0 mirrors the two dim halves and moves nothing
else — that is the cross-check that the map is not an artefact of one pairing. In the kernel the map has exactly
one spelling, `fattn_h_dim()`, beside `fattn_c_col()`.

Device check used on this (the one allowed, and it is spent):

    tools/gpu_lock.sh acquire pvf16-map            # util at acquire: 91 %
    tmp/pvf16_map/a10_pvf16_map_probe                    > tmp/pvf16_map/lowfirst.txt
    tmp/pvf16_map/a10_pvf16_map_probe --opsel-high-first > tmp/pvf16_map/highfirst.txt
    tools/gpu_lock.sh release pvf16-map
    python3 prototype/attn_percost/check_a10_pvf16_map.py --dump tmp/pvf16_map/lowfirst.txt \
            --swapped tmp/pvf16_map/highfirst.txt            # -> PVF16 MAP PASS

Wall 0.32 s for both launches. **No timing taken** — the probe prints values, not milliseconds, and none of its
output is a bandwidth or latency figure. The checker run was CPU-only against the saved dumps.

## 3. Compile-side witness

Built compile-only the way A11 built its baseline (`hipcc -O3 -Wno-unused-command-line-argument -I. -Iengine
--save-temps -c engine/kernels_attn.cpp`), read with `prototype/attn_percost/a11_read_vgpr.py` (`.amdhsa_next_
free_vgpr`, never the note-block `.vgpr_count`) and `prototype/attn_percost/a10_pvf16_isa_notes.py`, which pairs
each YAML note INSIDE its own entry and slices each body off the bare column-0 label — both because a naive
pairer reports another kernel's number, which is how `185 VGPR / 0 spill` got into A10 in the first place.

    kernel                           vGPU  alloc    LDS n.vgpr  spill  private    wmma_f32  wmma_f16  mul_f32  mul_f16  cvt_f32_f16
    attn_fattn_wave                   241    248  32768    178      0        0          17        0      146        0           48
    attn_fattn_wave_two               241    248  32768    200      0        0          18        0      146        0           48
    attn_fattn_wave_u8                241    248  20480    185      0        0          17        0      146        0           48
    attn_fattn_wave_two_u8            241    248  20480    221      0        0          18        0      146        0           48
    attn_fattn_wave_pvf16             243    248  32768    243      0        0           1       16       18       64          177
    attn_fattn_wave_two_pvf16         242    248  32768    242      0        0           2       16       18       64          177
    attn_fattn_wave_u8_pvf16          244    248  20480    244      0        0           1       16       18       64          177
    attn_fattn_wave_two_u8_pvf16      244    248  20480    244      0        0           2       16       18       64          193

**Criterion 1 — the default is inert, proved not asserted.** The four non-`pvf16` rows read 241 / alloc 248 with
LDS 20480 (`_u8`, the shipping kernel) and 32768 (staged), identical to the HEAD baseline built the same way in
`/tmp/pv_base`. The knob adds four kernels and does not touch the codegen of the four that ship.

**Criterion 2 — the knob=1 side, and the premise it falsifies.** LDS is unchanged (20480 / 32768 per qstage
side) ✓. `v_wmma_f32` drops from 17 sites to 1 — the one that remains is the score leg, which the knob must not
touch ✓ — and 16 `v_wmma_f16_16x16x16_f16` appear ✓. In the round body `v_mul_f32_e32` falls 146 → 18, because
the 128 per-round F32 multiplies are gone, and what replaced them is 64 `v_pk_mul_f16`: the compiler DID
cooperate, two halves per instruction, so D1's "half the VALU of that loop" survives the reading. What D1 did
not price is the drain: +129 `v_cvt_f32_f16_e32` per launch to widen the halves back into the F32 transpose
stage, so the trade is −64 slots per **round** against +129 per **launch** — a round loop of R rounds pays
−64R + 129, which is a win for R ≥ 3 and a loss below that. Spill stays 0 and scratch stays 0 in all eight.

The two-issue shape is verifiably llama's, not a similar-looking one: the 16 issues land on **8 distinct D
blocks, each used exactly twice**, with the same B operand in all sixteen (`v[97:104]` — one P fragment) and
`op_sel:[0,0,1]` on the second eight:

    v_wmma_f16_16x16x16_f16 v[41:48], v[106:113], v[97:104], v[41:48]
    v_wmma_f16_16x16x16_f16 v[41:48], v[114:121], v[97:104], v[41:48] op_sel:[0,0,1]

**The register claim did not survive.** `A10-RF-LADDER.md` §6 measured −64 for the accumulator swap in a
standalone probe (219 → 155 with Q resident, 177 → 113 without) and D7 booked that as the door a later
Q-in-registers-as-F16 spelling fits through. In the shipping kernel the reservation does not move:

| accumulator registers live | spelling | `.amdhsa_next_free_vgpr` |
|---|---|---|
| 128 (F32, shipped) | `attn_fattn_wave_u8` | **241** |
| 64 (F16, this knob) | `attn_fattn_wave_u8_pvf16` | **244** |
| 64, rescale fold neutralised (`/tmp` variant, never committed) | 〃 | 242 |
| 32 (F16, tile count halved again, `/tmp` variant) | 〃 | **241** |

Halving the accumulator a second time changes the reservation by nothing. The peak live set of this kernel is
not the accumulator: the allocator spends the freed registers on the two-A-fragment issue shape and the drain's
widenings, and LLVM's own note count says so bluntly — 185 for the shipped kernel against 244 for this one, even
though the accumulator is half the size. At the driver's granularity of 8 both sides allocate **248** and the
occupancy binder remains LDS at 3 blocks/CU either way, so the change is register-neutral in every sense the
machine can see.

Consequence, stated rather than smoothed: D7's table row "Q in registers, f16 accumulator: ~244 vs 256, fits
with ~12 spare" is not a door — 244 is what this kernel costs with NO Q resident, and 128 registers of resident
Q does not fit in the 12 that are left. A11's §2 mass (672 of 2,123 slots per wavefront-round) is still there;
this change does not unlock it. Whether the knob stays in the tree is now a decision for the main agent, not for
me to reverse silently: what it delivers unconditionally is the F16 P·V path, the measured D map, and the
format's numerics under the existing bands, at zero register cost and zero expected throughput change.

## 4. CPU mirror — `prototype/attn_percost/a10_pvf16_mirror.py`

It is not a fourth reference: it imports `prototype/attn_decode/floor_probe.py` and reuses `rows()`,
`scores_in_order()`, `bf16_ulp` and floor_probe's own case population — 48 `dec8` cases (8 decode steps × 6
layers) plus 5 `p300` long-cache rows, enumerated not typed — 108,544 output elements over 53 cases. One score
matrix per case feeds both arms; the max/fold/exp/P/denominator are shared expressions; the ONLY difference is
where the P·V partial accumulates. FATTN_MLANES = 16 lanes a round, as the kernel does. It takes no device time
and certifies no device run; it bounds the format change.

```
1. BAND      9,873 / 108,544 elements differ (9.096 %), 401 outside a no-excuse band, worst 14,508 BF16 ULP,
             cos >= 0.99999441, meanrel <= 2.23e-03
             pessimistic model (16 sequential F16 adds a round): cos >= 0.99998834, meanrel <= 3.72e-03
             vs the PIN:  F32 arm cos >= 0.99999159  meanrel <= 3.39e-03  worst 29,627 ULP
                         F16 arm cos >= 0.99999176  meanrel <= 3.67e-03  worst 29,622 ULP
2. ARGMAX    1 of 424 head-rows moves its argmax over DH
3. RANGE     max |acc/l| = 22.80 against fp16's 65,504: 0 overflows; 0 values under flush-to-zero
4. CHAIN     with the fold: 2,912 / 630,784 adds never change the accumulator (0.462 %) — same rule, F32 form: 1
             without the fold: first add dropped at round 1 / 13 / 99 (min / median / max over 53 head-rows),
             most adds dropped by round 53 / 2,035 / 3,552
```

Reading, with the caveats attached where they belong:

* **Band.** The arm-to-arm distance is 5.6e-6 in cos and 2.2e-3 in meanrel — against the bands in force
  (`cos >= 0.9995`, meanrel hard ceiling 5 %) that is not close, and it is a *delta*, not the gate's own
  comparison. The line that matters is the last two: the F16 arm's distance to the pin is cos 0.99999176 against
  the F32 arm's 0.99999159 and meanrel 3.67e-3 against 3.39e-3, i.e. the format change costs about 8 % of the
  error the streaming form already carries, and does not open a new order of magnitude. That is the admissibility
  claim, and the device gate is what has to confirm it per fixture with the allowance arithmetic.
* **Where it concentrates.** Only two head-rows exceeded `off_rel` 1e-2, and both are cancellation, not noise:
  `p300/row276/L3` head 2 dim 64 (off_rel 0.0527, |out| 1.055 → 1.062 with a row peak of 1.117) and
  `p300/row191/L3` head 0 dim 36 (0.0183, 0.252 → 0.2539 against a row peak of 0.7578). Both are long-cache
  prefill-derived rows from `p300`, not decode steps — the same population the streaming route is about. The
  large ULP counts (worst 14,508 arm-to-arm, 29,622 against the pin) are BF16-integer distances on elements
  whose relative error is inside the band; ULP alone is not the verdict, and AGENTS' cancellation row is why
  this is said out loud rather than left to the reader.
* **Range.** `max |acc/l| = 22.8` is three orders of magnitude below fp16's 65,504 and nothing flushed to zero,
  which is the same census D14 took over the dumps and the reason the fp16 rule needed no new band.
* **Chain.** With the fold in force the F16 accumulator drops 0.46 % of adds against the F32 form's ~0 % — each
  dropped add is below half a ULP of the running value, so below 4.9e-4 relative at that element, and the
  aggregate they could account for is far under the meanrel above. Without the fold the first add is dropped at
  round 1 in the worst head-row and by round 13 in the median, and past ~2,000 rounds (16 lanes a round, so
  ~32k lanes — the sweep length §6 names) most adds are dropped, which reproduces §2b's 2^11-exactness bound on
  real addends instead of on the probe's synthetic step. **The per-round fold is what makes this form legal, and
  it is exactly where it was.** The round-cycling in the counterfactual holds the addend scale fixed to reach a
  length the pinned fixtures do not contain; the fixtures exercise 18–277 lanes = 2–18 rounds, so that part is
  an extrapolation at fixed scale, labelled as one, and §2b's ~256 is the same kind of bound.

## 5. What could not be done here, and why

* No device gate, no paired burst, no `ms`. Worker device budget was one correctness-only check under a minute;
  it went to the D-map probe (§2). Every number in §3 and §4 is compile-side or CPU-side.
* `speccheck/run_all.py --quick` (11 gates) after the change: **11 run, 0 failed**. The full 26-gate run was
  not re-made: nothing in `speccheck/specimpl.py` or a speccheck gate file was touched, which is the standing
  budget rule rather than a shortcut.
* `engine/gate.py --help` raises `ValueError: unsupported format character 'v'` from argparse — **pre-existing at
  HEAD** (reproduced against `git show HEAD:engine/gate.py`), not introduced here, and unrelated: some other
  help string contains a bare `%`. Flagged, not fixed, because fixing it is a separate topic.
* The census tooling needed a fix on the way: my first reads of `a11_read_vgpr.py` were piped through
  `tail -1`, and `attn_fattn_wave` is a prefix of `attn_fattn_wave_pvf16`, so `tail -1` reported the wrong
  kernel — the exact trap that tool's own header documents, walked into by the reader rather than the tool.
  `a10_pvf16_isa_notes.py` keys on the full mangled name and prints one row per kernel, always, and its
  `--selftest` refuses a slicer that finds stubs or a WMMA kernel with no matrix instruction.

```bash

engine/build.sh                               # ~19 s, both binaries

# CANARY FIRST, in the same window as the numbers (AGENTS, 2026-10-17 stale-binary row):
# the ATTN_FATTN line must print pv=f32 with vgpr=241 on the base side and pv=f16 with vgpr=244 on the

tools/gpu_lock.sh acquire a10-pvf16
.venv/bin/python engine/gate.py                               # default side: knob inert, HEAD's own machine code

tools/gpu_lock.sh release a10-pvf16
```

The paired timing belongs to a harness modelled on `prototype/attn_percost/run_ab_a6g1.sh` (one binary, two
sides, both legs inside one lock hold — a ruler re-taken in a different window is not an A/B), with

```
ARGS="--steps 0 --time-waves --gemm lt --gemm-pins all --wave-rows 512"
PV_ARG=" --attn-fattn-pvf16 1"
```

and, as that harness does, the geometry fields (`lds`, `vtiles`, `wave_rows`, `split`, `fattn_rows`) asserted
IDENTICAL across the two sides while `pv=` and `vgpr=` are asserted to DIFFER. `vtiles=` deliberately still
reports `FATTN_VTILES` = 16 — the output-tile coverage is the same in both forms, which is the whole point; the
accumulator's width is what `pv=` names. Expect the honest verdict to be **~0 % on the `attn` family row**: the
atom is free at equal coverage and the fold's VALU saving is paid back at the drain, so the read that matters is
whether the numerics stay inside the floors, not whether the milliseconds move.

## 7. Residual risks

1. **The register premise is falsified at this placement and D7 has not been re-priced.** If the Q-in-registers
   bet is still funded, it needs a fresh register derivation that does not assume this knob frees 64 registers.
2. The mirror models the hardware's intra-round summation at its two bounding ends (one rounding at the add; 16
   sequential F16 adds). If the matrix unit is *worse* than both — e.g. it truncates rather than rounds — the
   real numbers are outside what this bracket covers, and only the device gate can say.
3. Long-context behaviour is extrapolated, not measured: the pinned fixtures top out at 277 lanes and the chain
   section cycles rounds to reach thousands. The gate's wide fixtures are the real test of §6's bound.
4. The knob is orthogonal to `--attn-fattn-roll` and `--attn-fattn-qstage` and all eight combinations compile and
   are launchable, but only `roll=single × qstage=unstaged8` is the shipping default, so the other six have never
   run on a device at either knob value.

## Main-agent device pass (2026-10-20): inert witnessed, numerics tolerated, and the register prize is gone

One `gpu_lock` hold each, blocking, zero subagents. Prompt 2,048 ids, `--steps 4 --attn-fattn 1`, five logits
dumps per arm; harness `run_a10_device.sh` → `run_a10_pvf16_device.sh`, `run_a10_pvf16_timing.py`.

**A. Inertness — witnessed, not asserted.** The pre-change binary (`/tmp/ab_res/base_run`, same tree before the
knob) against the new binary at its default: **all five `logits*.bin` and `sampled.txt` byte-identical** (`cmp`
per file, no `DIFFERS` line). That is the whole justification for the template axis existing.

**B. Numerics — knob 1 vs knob 0 on the same prompt.**

| dump | cos | meanrel | argmax | ndiff | max abs |
|---|---|---|---|---|---|
| logits2047 | 0.99991077 | 9.07e-2 | 40 → 40 SAME | 248,318/248,320 | 0.222 |
| logits2048 | 0.99991012 | 9.56e-2 | 40 → 40 SAME | 248,320/248,320 | 0.222 |
| logits2049 | 0.99988568 | 1.91e-1 | 40 → 40 SAME | 248,318/248,320 | 0.240 |
| logits2050 | 0.99982774 | 1.52e-1 | 40 → 40 SAME | 248,320/248,320 | 0.269 |
| logits2051 | 0.99986529 | 1.23e-1 | 40 → 40 SAME | 248,319/248,320 | 0.253 |

`ndiff` ≈ everything is the expected signature of a re-associated accumulation and carries no information here
(AGENTS.md: ndiff is blind to chains); the decision-relevant reads are argmax — **unchanged on all five steps**
— and the token stream, where **no token differs**: `diff` on `sampled.txt` moves five lines and in every one
of them only the printed logprob field changed (`2047 40 40 23.62…` → `… 23.53…`), the ids column is `40 40` on
both sides. The CPU mirror's prediction (cos ≥ 0.99999 on the head-row aggregate, ~8 % further from the pin than
the f32 arm, no new order of error) is consistent with this. **No band was touched, and none needed widening on
this fixture** — which is a statement about this fixture, not a device-wide admission: the derived-population
`gate.py` run at `--attn-fattn-pvf16 1` is still owed before the knob is anything but inert.

**C. Throughput — not a claim, and said so.** 16,384 lanes, paired and interleaved, best-of-3:
f32 arm 2,841.2 / 2,844.9 / 2,875.8 ms (best **2,841.2**); f16 arm 2,743.5 / 2,823.3 / 2,855.6 ms (best
**2,743.5**), i.e. **−3.44 %** for f16 on best-of-3. **The ranges overlap** (the f16 worst, 2,855.6, is worse
than the f32 best), which is exactly the dispatch-bound bimodality `bench/performance-status.md` §6 warns
about, so the honest reading is "best-of-3 favours f16 by ~3.4 %, plausibly the packed rescale, not resolved by
this window". Anyone who wants the speed claim owes a wider-N paired window; nobody should book −3.44 % into
the ledger on these six reps.

**D. The finding that changes the plan, confirmed by the main agent independently.** `a11_read_vgpr.py` on the
current tree: `attn_fattn_wave_u8` reserves **241** VGPR, `attn_fattn_wave_u8_pvf16` reserves **244** — the
accumulator going 128 → 64 does **not** reduce the reservation, it *raises* it by 3, and both allocate 248.
So `A10-F16-IMPL.md` **D7's premise is false as written**: the "64 registers freed, so Q-in-registers-as-F16
fits with ~12 spare" arithmetic used an isolated probe, and in the real kernel the allocator spends the freed
registers on the round's other live values. Halving the accumulator a second time (4 tiles, 32 registers)
still reads 241, which is the direct proof that the accumulator is not the binding live-set. What the f16
change actually is: **register-neutral, numerics-tolerated, best-of-3 ~3.4 % faster and unresolved** — an
inert knob whose only demonstrated property is that it costs nothing at default and may buy a few percent at
arm. If a future Q-in-registers attempt is made, it must price its own registers from the live kernel rather
than inheriting D7.
