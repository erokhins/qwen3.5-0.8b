== 2. resident or re-read?  RE-READ, EVERY TOKEN, because there is no token loop to be resident in
  The shipped form's only loops are the two `for (int i = 0; i < D; ++i)` walks over the state
  inside ONE launch (gdn_decode_kernels.h:179); the next token is the next launch
  (engine/decode_step.cpp:677 -> engine/decode_step.cpp:692), so the state is read from global on every
  token by construction. It is not a staging choice either: a block owns one head's 128x128 F32
  strip = 64 KiB, which is the whole LDS budget of a CU (65,536 B), so the shipped geometry
  CANNOT hold the state across tokens. The engine does own a resident form
  (`--gdn-scan collapse`, engine/gdn_collapse_kernels.h) and it is measured, in §4 below.

== the ceiling test, and what it can and cannot say
  demanded bytes at 534.54 ms = 438.4 GB/s total (433.9 GB/s of it state)
  the part moves 240 GB/s read / 210 GB/s copy at 1 GiB (devices/strix-halo-memory-bandwidth.md, `iGPU, 1 GiB`)
  the SAME access pattern with the state warm measures 876 GB/s at an 18 MiB working set
  and 255 GB/s once tiled to 108 MiB (prototype/gdn_decode/results.md, Performance)
  EXCEEDED: 438.4 > 240 GB/s. That is not a bandwidth wall, it is a
  units confession — AGENTS.md's D21 row: DEMANDED BYTES ARE NOT DRAM BYTES. L1/L2/MALL
  absorb the reuse (hipGetDeviceProperties calls L2 2 MiB; the warm row above proves a
  larger cache the query does not report is holding the 18 MiB). So the demand figure is
  admissible ONLY as the ceiling argument this section makes, never as the wall.
  against the measured warm-state rate the same shape achieves, the demand is 50.0 % of what the box demonstrably moves. Traffic therefore cannot be the binding constraint: the kernel asks for less than half the bytes-per-second the identical access pattern is measured delivering when the state is warm, and each launch still
  takes 7.25 us.

== the direct witness, which is better than any ceiling: the traffic has already been removed
  `prototype/gdn_collapse/results.md` §4 measured route A, which keeps the state resident in
  LDS: state round trip 38.7 GB -> 75 MB per 1024-lane wave (a 516x cut, essentially all of it) bought 125.36 -> 112.04 ms
  = 1.119x of the family.
  Attribute all 13.32 ms of that to traffic and a 2x cut is
  still worth at most half of it. Attribute it the way the launch arithmetic says to — route A
  also replaced 18,432 launches with 36, and the empty-kernel dispatch floor
  is 1.75-2.08 us (devices/strix-halo-memory-bandwidth.md §0c), which more than covers the
  13.3 ms on its own — and traffic bought close to nothing at all.

== 5. what a 16-bit state would buy, priced with measured elasticities
  bytes: it halves the STATE term, not the demand — the state is 99.0 % of the demand, so the wave's demand
  falls from 234.354 GB to ~119.602 GB.
  demand rate would fall from 438 to ~224 GB/s — i.e. from above the 240 GB/s package ceiling to about it, and the ceiling was
  never what bounded the kernel (§3). A saving in a quantity that is not the constraint.
  instructions: the recurrence consumes the state as F32 in FMA chains. An F16/BF16 state means a
  conversion per state access, and the accesses are per thread per token-step: 2 x D reads + 1 x D
  writes = 3 x 128 = 384 conversions on a 1523-slot bill (isa_census.output.txt) = +25.2 % slots. Packing two halves per 32-bit access cannot avoid it: a thread
  owns ONE d_v column j and walks i, so the pair it would need is in a different thread — packing
  the state means re-cutting the thread mapping, i.e. a different kernel, not a dtype flag.
  D25's measured elasticity is ~0.8 (a -2.0 % slot cut returned -1.6 % of time), so +25 % slots
  is roughly +20 % of the family ~ +108 ms, against a traffic saving the
  §4 witness bounds at well under 13 ms for the WHOLE traffic term.
  It is a net loss on this repo's own numbers, twice over. And it is already named as a defect:
  `engine/gdn_collapse_kernels.h`'s fail-closed negative `rc_state_bf16` is 'the cheap *the state
  is big, halve it* mistake', injected on purpose to break bit-identity. A 16-bit state is also a
  numerics change with NO existing range evidence: §10.1 G3 gates `state_new`, but the pinned
  `decode*.state_fp.npy` files are FINGERPRINT rows (tools/reference_dump.py -> tools/state_fp.py),
  not raw values, so `tools/fp16_range_probe.py`'s D14 census (peak 82.5, 794x margin) covers
  activations/logits/weights and says NOTHING about the state's dynamic range. Under D13 a
  16-bit switch is adoptable if the gates stay green; here the gates could not go green or red,
  because nothing pins the state's magnitudes. That is the missing measurement, not a band to ask
  for. RECOMMENDATION: do not fund it.

== 6. VERDICT
  TRAFFIC-BOUND: NO. The demand rate (438 GB/s) exceeds the package ceiling,
  which under D21 falsifies the traffic model instead of supporting it; the same access pattern
  is measured at 876 GB/s warm, so the demand fits in half of what is demonstrably
  available; and removing essentially ALL the state traffic in situ bought 1.119x (route A).
  LATENCY-BOUND on the per-token dependency chain: STILL THE LIVE READING, and still unmeasured.
  Everything this census could do without a device raises it: traffic is out, instructions are out
  (D25, 1.0159x), launches are out (route A removed 18,396 of them for 13 ms), the working set is
  inside the cache that holds it. What is left is the chain.
  FALSIFIER THAT FOLLOWS: the dependency-break probes in this directory (§9 of results.md).
  rec3 breaks the cross-token round trip at fixed volume (and a fixed bill: -1 slot), rec4
  shortens the two serial accumulator chains at fixed volume, rec5 does both, and rec6 is rec4's
  bill-matched control — same unroll-4 loop spelling, chain NOT broken, bit-identical to rec0 —
  because the census found rec4 10.5 % cheaper in slots and D25's elasticity says a bill that
  much is worth up to 8.4 % of time by itself. Read rec4 against rec6, not against rec0. If the
  probes move the clock, the chain binds and D30 items 1.4/1.5 get funded; if they all sit in the
  noise, `gdn_rec` needs a model that D23's census has still not named, and the counters pass
  (HANDOFF.md §4) is next, not more levers.
